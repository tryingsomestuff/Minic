Minic technical documentation

This is a source-oriented developer guide to Minic: its architecture, state representation, search, evaluation, move selection, time allocation and tooling. Start here, then follow the chapters rather than reading every source file in alphabetical order.

Documented source

Reviewed on 2026-10-06, against Minic 3.47, commit 1210cdbb and the working-tree changes present during this review. In particular, this guide includes the not-yet-committed GameInfo search-score persistence and booming/moobing changes. Four-distance continuation history is in the base commit. These details matter when comparing this guide with older binaries.

The guide describes the usual desktop configuration in config.hpp. Small-memory targets, compiler/platform conditions and runtime options can change it. The source links and named functions are the authority for exact conditions and current constants.

Startup

minic() initializes the engine before dispatching a developer command or a protocol loop. The significant order in init() is:

  1. Distributed runtime, options and logging.
  2. Zobrist keys and TT allocation.
  3. Board/attack masks, optional magic attacks, KPK and material knowledge.
  4. Evaluation configuration and the thread pool.
  5. Late distributed initialization, Syzygy and NNUE loading.
  6. COM::init(), root-position setup and optional energy monitoring.

Options and network availability affect later initialization. Merely compiling WITH_NNUE does not establish DynamicConfig::useNNUE; successful loading does. Similarly, compiled Syzygy support does not imply that table files are available.

At shutdown, the engine stops workers, waits for them, clears the pool's workers, finishes distributed operations and finalizes monitoring/logging. Do not destroy shared root information or weights while workers still reference them.

Three configuration layers

Build-time gates in config.hpp remove or include code. Examples are NNUE, Syzygy, MPI, timers and tuning support.

Algorithm switches and parameters in searchConfig.* control search heuristics. Many parameters are constants normally and become mutable in a search-tuning build through CONST_SEARCH_TUNING. Local constexpr bool switches in depthPolicy() are a further layer: a descriptive branch can exist but be compiled away.

Runtime options live in DynamicConfig, registered through Options. They include hash sizes, threads, MultiPV, NNUE file/scaling, contempt, skill and variant settings. Some callbacks are delayed until isready; some operations cannot safely run during a search. Read the registration and callback together, not just the global's initial value.

UCI: position -> search -> bestmove

For a normal sequence such as:

ucinewgame
position startpos moves e2e4 e7e5
go wtime 60000 btime 60000 winc 500 binc 500

ucinewgame calls COM::init(), which resets the protocol root, worker game state and GameInfo. The optional previous-game PGN write precedes the reset.

position reads the initial FEN and applies the supplied moves to COM::position. In the documented working tree, it builds a temporary GameInfo; replace() preserves optional scores along the old history's unchanged prefix. A different initial position or divergent move invalidates scores beyond the common prefix.

go populates TimeMan limits and calls COM::thinkAsync(). That constructs ThreadData, allocates the initial time budget and passes the data to ThreadPool::startSearch(). Workers receive position copies, not ownership of the GUI position.

The main searcher runs iterative deepening, eventually selects a result and publishes the searched root's score. COM::receiveMoves() then reports the move. An implementation detail is that it also applies the move to COM::position, even for UCI; the next position command reconstructs the authoritative game state. Do not interpret this as fully stateless UCI internals.

XBoard differences

XBoard keeps a more explicitly stateful game: force/analyze/play modes, side-to-move bookkeeping, opponent moves and engine moves. receiveOppMove() and moveApplied() append played positions to GameInfo.

Undo/remove uses replay(): reconstruct the remaining move sequence and retain scores only in the retained prefix. Setting a board or starting a new game resets history rather than inventing moves preceding the supplied position.

Move legality and variant behavior are shared with the engine core; the protocols do not each maintain independent board implementations.

The main searcher is not the protocol thread

Even Threads = 1 has a protocol/control thread and a search worker. Each Searcher owns a std::thread, mutex and condition variable; searcher index zero is what isMainThread() means.

The protocol loop continues accepting commands while the worker searches. The main worker starts helpers; an atomic start lock delays them until the driver releases them. Workers normally explore their own trees and communicate indirectly through the TT, not through a centrally split move queue.

Read time and parallelism before changing publication or shared-state synchronization.

Developer and auxiliary paths

DEBUG_TOOL enables CLI operations such as perft, SEE, evaluation, qsearch and analysis. The desktop configuration forces this gate on. WITH_TEST_SUITE adds tactical/position-suite machinery; data generation/conversion and tuning have additional gates.

Not every searchDriver() invocation represents the live GUI game. subSearch marks auxiliary work; postMove controls move reporting. The current score-history integration uses both to avoid recording unrelated analyses. postMove is a practical gate, not a semantic proof that a root belongs to GameInfo; the setter separately validates membership.

Publication is not the same as computation

Working scores and PVs change during aspiration retries and incomplete iterations. Reporting a bestmove chooses a final root result, potentially with worker voting. GameInfo::setSearchScore() records that chosen result only after its root validation; it is not updated for each PVS node or each transposition encounter.

Three consumers therefore need different data:

Consumer Required state
Recursive search Current position, local stack context, current window.
Iteration time policy Completed-depth root scores and instability estimates.
Across-move time policy Optional final scores for earlier searched game roots.

Using one consumer's storage for another conflates search attempts, completed analysis and actual game history. The absolute-ply stack is useful for local tree continuity, but it is not a durable score ledger for the GUI's game.

Architectural tradeoffs

The engine favors compact types, templates and explicit state over a generic framework. Board state is copy/make, evaluation combines specialized knowledge with NNUE, and most search heuristics operate in one large PVS implementation. This reduces some indirection but makes ordering and shared invariants important.

A local change can have non-local consequences: move scores affect LMR, castling encoding affects histories, evaluation selection affects available attack data, and game-history publication affects timing. These are the boundaries the remaining chapters make explicit.

Positions, moves and legality

Coordinate and type conventions

Squares are a1 = 0 through h8 = 63; file is square & 7, rank is square >> 3. White/black are 0/1 and ~color flips them. Pieces use signed color encoding; helpers such as PieceIdx() map them into table indices. Do not remove color by taking an absolute piece value when the table expects colored pieces.

Type Representation
Square Signed 8-bit; negative values also serve as invalid squares/deltas.
DepthType Signed 8-bit; MAX_DEPTH = 127.
ScoreType Signed 16-bit; arithmetic often needs a wider intermediate.
MiniMove Signed 16-bit move identity.
Move Signed 32-bit identity plus ordering score.
Hash, BitBoard Unsigned 64-bit.
TimeType Signed 64-bit, generally milliseconds.

The reserved move-type bits, not simply a sign test, distinguish invalid/null moves. Use isValidMove(), sameMove() and conversion helpers instead of inventing encodings from these typedefs.

One board, several synchronized representations

Position contains:

  • _b: a 64-square mailbox, convenient for piece identity.
  • _allB: piece-kind bitboards, combined with allPieces[color] for color.
  • Material counts and derived material fields.
  • Full position hash h, pawn-and-king hash ph, and optional per-color non-pawn hashes nph.
  • Side to move, kings, castling rights, en passant, last move and game counters.
  • A non-owning RootInformation* and, with NNUE, an evaluator pointer.

Attack calculations use precomputed masks and occupancy-sensitive sliding attacks. WITH_MAGIC selects the normal desktop magic-bitboard implementation; alternative paths are available for other builds.

Mutating the mailbox alone is never enough. Board, bitboards, material, king locations and hashes must describe the same position before the next search or evaluation.

Game ply versus search height

Reading a full FEN sets:

halfmoves = 2 * (fullmove_number - 1) + 1 + (side_to_move == black)

Thus the starting position has halfmoves = 1. moves is the fullmove counter; fifty counts reversible halfmoves since the last pawn move/capture.

The search stack is indexed by absolute halfmoves, whereas killers and search limits use relative height. PVS and its pruning quiescence search assert height == halfmoves - rootHalfmoves. Real moves and null moves advance both coordinates by one; same-position searches (null-move verification, IID and singular-extension probes) preserve height while changing depth or windows. Relative-height guards therefore also enforce the corresponding stack boundary. Standalone qsearchNoPruning() tools do not use this root-relative contract.

initRootPositionOnStack() records rootHalfmoves, clears pre-root stack slots and initializes the root's evaluator. Real game history is in GameInfo, not in those discarded slots.

Copy/make and the stack

Minic does not normally make a move and then undo it on a single board. initChildPositionOnStack(parent) copies the parent into the next absolute-ply slot; applyMove() modifies the child. A rejected child can be discarded and overwritten on the next attempt.

The important pattern in the main move loop is:

copy parent into child stack slot
construct MoveInfo from the pre-move child
apply board move with NNUE update deferred
reject if illegal
apply pruning decisions
copy/associate child evaluator and update NNUE
search child

Deferring NNUE work avoids updating accumulators for moves that are never searched. It does not permit searching a child with an evaluator still pointing at the parent.

Same-position singular probes reuse stack slots. The TT-move path therefore initializes its child after the singular probe, not before it.

Move encoding

The low 16 bits contain six from bits, six to bits and four type bits:

identity = (from << 10) | (to << 4) | type
Move     = identity plus a signed ordering score in the upper 16 bits

Types distinguish ordinary quiet moves, captures, en passant, four quiet promotions, four capture promotions, four color/side castlings and a reserved type. Use Move2MiniMove() when retaining identity without its transient score.

Ordering scores can change between searches. Equality of scored integers is not generally the right way to decide whether two chess moves are the same.

Castling is encoded king-to-rook

For castling, the stored destination is the rook's initial square, not the king's landing square. This supports Chess960 positions where the initial king and rook locations vary.

RootInformation records king/rook origins and castling permission masks. correctedMove2ToKingDest() and correctedMove2ToRookDest() recover the landing squares: c/g for the king and d/f for the rook.

Move generation checks occupancy of both paths and attacked king-path squares. Application relocates both pieces and updates rights/hashes. Preserve cases where a starting square is also another piece's landing square; orthodox-only assumptions are unsafe.

Histories indexed by the moved king's destination must use the corrected king square. A raw castling to can instead select the rook or an empty square after application.

Generation is not final legality

MoveGen::generate<phase>() supports:

Phase Actual generation
GP_all All pseudo-legal move categories, including quiet promotions and castling.
GP_cap Captures, capture promotions and en passant; not ordinary quiet promotion pushes.
GP_quiet Non-captures, including quiet promotions and castling.
GP_evasion King moves and candidate captures/blocks of checkers, including special handling paths.

Evasion masks narrow the candidates, but application remains the legality filter. En passant can expose a sliding attack when two pawns leave their squares, so destination-only reasoning is insufficient.

isPseudoLegal() is especially important for moves recovered from a compressed TT key. It is not a replacement for the post-move king-safety test.

applyMove() and MoveInfo

MoveInfo snapshots the move's source/destination pieces, type, kings and en passant state before mutation. applyMove() dispatches by type, updates representations and checks whether the moving side's king is still attacked. If illegal, it returns false after modifying the child; it does not restore that object.

On success it removes/creates en passant state, flips side to move, updates hashes/counters and optional NNUE state. Captures and pawn moves reset fifty; other moves increment it. An en passant target is retained after a double push only when an adjacent opposing pawn exists.

Promotions update both material and hash classes: the pawn disappears and a non-pawn piece appears. En passant removes its victim from a square different from to. Castling changes both king and rook representations.

applyNull() is not a legal game move. It flips side/hash, clears en passant, records NULLMOVE and advances game-ply counters without moving pieces. It does not run the ordinary capture/pawn/fifty update sequence.

Hash domains

Full Zobrist hashing covers colored pieces, side, castling rights and en passant. It does not encode the fifty-move counter. computeHash() normally returns the incrementally maintained value; debug modes can verify it.

computePHash() covers pawns and kings, because cached pawn evaluation contains king-location-dependent information. It is not a pawn-only key. nonPawnKey() covers one color's non-pawn pieces with kings excluded.

Excluded searches perturb the PVS key with hashes of excluded moves. This keeps ordinary and exclusion-specific bounds from being treated as interchangeable.

NNUE ownership and invalidation

Ordinary moves insert/erase feature rows in both perspective accumulators. A king move changes the feature coordinate system for its perspective and requires a rebuild; castling must also account for the rook move.

Position copies keep a pointer to an evaluator; they do not deep-copy it. Search code must use the evaluator stack helpers before incremental updates. Standalone analysis/evaluation positions need their own associated evaluator. The shared root metadata must also outlive all copied positions.

Why MoveInfo must precede mutation

After a capture the victim no longer exists on the destination; after EP the old target may have been cleared; after a king move the old feature frame has changed. MoveInfo captures that pre-move information once and is then passed to board and NNUE updates. Reconstructing it from the completed child loses exactly the information the incremental updater needs.

Failed applyMove() is not an undo operation. It can leave the disposable child mutated before rejection; recopy the parent for a new candidate. Do not reuse rejected child state as if it were unchanged.

Attack generation backend

attack.hpp provides the same coverage/attack API over magic bitboards or hyperbola quintessence. Coverage is geometry under occupancy; attack intersects coverage with a supplied target mask. It does not itself establish move legality.

Magic tables allocate 64-by-512 bishop and 64-by-4096 rook slots. With 64-bit bitboards that is 256 KiB plus 2 MiB before masks/magic metadata. BMI2/PEXT is selected only under the explicit architecture guards; otherwise the masked occupancy is multiplied by a magic number and shifted.

between[a][b] excludes both endpoints. Using it to test blockers therefore has a different contract from testing the ray's target square.

Change checklist

When adding a move category or changing transition logic, check generation, pseudo-legality, application, all hash domains, material, castling/EP counters, NNUE updates, SEE, ordering, protocol conversion and tests. Perft should cover legal transitions; special-move searches should also verify legal PV/bestmove output and incremental evaluation consistency.

Negamax, alpha/beta and bounds

Search scores are from the current side's point of view. Descending a ply negates both result and window:

score = -search(child, -beta, -alpha)

Alpha is the best established lower threshold; beta is the cutoff threshold. A fail-high proves a lower bound for this window, not a globally exact score. B_alpha is an upper bound, B_beta a lower bound, and B_exact an exact window result. Many returns are fail-soft, but some heuristics deliberately return alpha/beta or a margin-adjusted estimate.

The template pvs<pvnode>() specializes PV/non-PV behavior. The cutNode hint affects selectivity; a PV flag, cut-node hint and TT-PV flag are related but distinct inputs.

The driver: iterative deepening and aspiration

The driver keeps the latest completed first-PV result and progressively searches depths 1, 2, ... up to its target. Skill settings can limit depth or nodes. Nodes limits are temporarily disabled for depth 1 to obtain a usable initial result. The depth ceiling reserves headroom below MAX_DEPTH.

After the configured aspiration minimum depth, search starts with a narrow window around the prior iteration's score. The initial half-width is:

aspirationInit + max(0, aspirationDepthInit - aspirationDepthCoef * depth)

On fail-low the window expands downward and the search depth is restored. On fail-high beta expands and the retry may be a ply shallower. Delta growth also depends on game phase; sufficiently wide windows become mate-range windows. These retries are not the adaptive LMR re-search experiment in TODO.

MultiPV repeats searches with previously selected root moves excluded. Separate scores/PVs are retained per line; only the first line updates the main reported best result. Output during failing aspiration windows is provisional. Interrupt handling must preserve an already valid result instead of publishing STOPSCORE.

After iterative deepening, local SMP vote selection can replace the main worker's result with another worker's supported/deeper line. Strength-limiting move selection is a separate path.

PVS control flow

The broad order inside pvs() is:

  1. Periodic stop/time checks; node context initialization.
  2. Height/depth limit, interior draws, and qsearch at depth <= 0.
  3. Node count, mate-distance window clipping and continuation-context lookup.
  4. Hash construction, endgame classification, TT probing/cutoffs and Syzygy.
  5. Static evaluation, optional TT estimate substitution and correction.
  6. Attack/mobility data, improving state and forward pruning.
  7. Null-move/ProbCut attempts, IIR and threat bookkeeping.
  8. Root tablebase list or TT move, including singular probing.
  9. Remaining move generation, scoring, legality, pruning and PVS/LMR searches.
  10. Terminal/fifty handling, correction learning and TT storage.

Early returns are intentional. Histories or TT entries are not necessarily updated on every path.

Evaluation values are not interchangeable

The raw static score is stored in stack[p.halfmoves].eval before TT search-score substitution. staticScore backs up that value.

evalScore can subsequently become a TT search result when its bound supports using it as a better estimate. evalScoreIsHashScore records that distinction. correctedStaticScore adds the pawn/non-pawn correction to staticScore; pruningEval uses that correction unless a TT search result has replaced it.

Never apply evaluation correction on top of a TT search result. Conversely, do not use a TT search bound as the raw evaluation of an ancestor for improving. The intended separation is important even where existing TT writes use the mutable evalScore variable; see tables for that caveat.

improving compares the raw static stack score with the same side's score two position plies earlier, outside check and only when height > 1. The asserted root-relative height invariant guarantees that this ancestor is not before the root. It is not currently a corrected-evaluation or NNUE-uncertainty comparison.

Threats, danger and inactive context signals

If evaluation did not supply attack data, PVS reconstructs it with evalFeatures(). haveThreats describes attacks on opposing pieces; goodThreats emphasizes favorable attacker/victim classes, such as pawn attacks on non-pawns or minor-piece attacks on rooks/queens.

Per-color danger contributes to the SEE pruning margins through dangerGoodAttack and dangerUnderAttack. However, the summed-danger threshold booleans currently record statistics rather than implementing a global "dangerous position: reduce less" policy.

Historical booming/moobing flags are copied into PVSData, but situationDepthCorrection is zero. Iteration-emergency flags are also forced false there, and the relevant LMR toggle is disabled. The current historical score repair therefore affects timing; it does not automatically enable all the experimental history/emergency selectivity branches.

Node-level forward pruning

These branches chiefly run at non-root, non-PV, non-check nodes, with additional mate-finder, depth, threat and zugzwang-risk gates.

Mechanism Decision and motivation
Reverse futility / static null move If evaluation exceeds beta plus a depth/phase margin, return a conservative margin-adjusted estimate without searching moves.
Opponent-threat pruning Similar fail-high shortcut when no sufficiently good opponent threat is detected.
Razoring If evaluation is well below alpha at shallow depth, use a qsearch verification; the no-own-threat path can return the razor threshold directly.
Null-move pruning Pass the turn artificially; if the opponent still cannot bring the score below beta, try a cutoff. Verification protects selected deeper cases.
ProbCut Test a limited number of promising captures against a raised beta, first in qsearch and then at reduced main-search depth.

The coefficient helper computes:

margin = (init[index1] + depth * slopeDepth[index1]
          + gamePhase * slopeGamePhase[index1]) * bonus[index2] / 256

Index meanings depend on the call: commonly TT-score substitution, improving or cut-node state. Parameter names alone do not establish those meanings. Depth activation ranges are checked separately.

Several margins use marginDepth = max(0, depth - TTdepth) when evaluation has been replaced by a TT search score; others use the nominal depth. The depth in the generic equation means the argument actually passed by that heuristic, not necessarily the unchanged requested depth.

Null move in detail

The current reduction is:

R = nullMoveReductionInit
    + depth / nullMoveReductionDepthDivisor
    + min((pruningEval - beta) / nullMoveDynamicDivisor, 7)
nullDepth = max(0, depth - R)

The artificial child is searched with a null window. The node must satisfy evaluation/baseline tests, cannot follow another null move, and uses material or mobility to reduce zugzwang risk. subSearch and exclusion searches are gated.

A high result at sufficiently deep search can trigger a same-position verification search. nullMoveMinPly and nullMoveVerifColor prevent recursive verification behavior for a portion of the subtree. Unverified mate-range null results can be capped to beta rather than asserted as actual mates.

The null child's TT move is also used as a refutation/threat hint for ordering. In HCE-only search, the static score after a null move may be derived from the parent plus tempo; this shortcut is not used with asymmetric NNUE.

ProbCut and IIR

ProbCut raises beta by probCutMargin + probCutMarginSlope * improving, generates captures and tries at most probCutMaxMoves. The child main-search depth is depth / probCutSearchDepthFactor. Captures generated here can be reused in the later main move list.

Its success-path TT write and capture-history bonuses are currently commented out. Do not document them as active learning.

IIR reduces depth by iirReduction at sufficient depth when no TT hit is available. It avoids spending the full nominal budget without a useful cache context. Traditional IID, which performs a shallower search to discover a move, exists but doIID is false.

TT move, singular extensions and multi-cut

A pseudo-legal TT move is attempted before generating the remaining list, unless excluded or constrained by the root tablebase list.

At sufficient depth, a non-root TT move with a useful lower/exact bound and enough recorded depth can receive an exclusion search. Other moves are searched around:

betaC = TT score - 2 * depth

If they fail below betaC, the TT move is considered singular and gains a ply. A stronger failure can grant a second ply, with cumulative-extension guards. The same mechanism has multi-cut and negative-extension branches when the evidence instead supports reducing work.

Triple extension and a separate cut-node negative-extension branch are commented out. Furthermore, every generic extension toggle in depthPolicy() is false: check, Botvinnik-Markoff threat evolution, mate threat, queen threat, castling, recapture, good-history and CMH extensions are not currently active there. The active singular path is separate.

Per-move pruning

After generation/scoring and successful board application, later moves may be skipped. Counters distinguish legal candidates from actually searched moves. The first eligible move receives stronger protection; later selectivity has additional advanced-pawn, check, killer and mate guards.

Mechanism Current use
Futility Skip later ordinary quiet non-check moves when static evidence is too far below alpha.
LMP Skip further eligible quiets after an improving/depth-dependent move-count limit.
Quiet history pruning Compare the scored move with a configured threshold; can set skipQuiet.
CMH pruning Test only the distance-1 context; missing context is not a bad-history signal.

skipQuiet does not make move generation deferred: the full remaining list already exists. Root, checking, promotion, en passant and castling behavior must be read through their actual move-type gates, not a generic quiet/capture description.

LMR and re-search

The precomputed base reduction approximates a logarithmic function:

Rbase = int(my_log2(depth * 1.6) * my_log2(moveNumber) * 0.4)

my_log2() is the repository's numerical approximation. The name is not a reason to substitute a different log function without retuning.

For ordinary quiet moves, active adjustments include not-improving, TT capture context, likely fail-high, move-ordering history score, former TT-PV and known endgame prudence. Capture reductions use capture history, bad-capture status, PV-node and improving adjustments. Many other named switches are false.

depthPolicy() returns:

nextDepth = depth - 1 + extension - reduction

It constrains reductions to avoid an accidental net extension on reducible moves and prevents a reduced child depth below zero.

Later moves first receive a reduced null-window search. If it exceeds alpha and there was a reduction, search again at depth - 1 + extension. A promising result then gets a full-window PV search when appropriate. This re-search target is fixed, not adaptively deeper/shallower according to the amount of improvement.

Good ordering affects both which moves are reduced and how much: changes to CMH weights are therefore not purely cosmetic list permutations.

Quiescence

Production qsearch() resolves tactical instability beyond the main depth. Outside check it uses a corrected stand-pat evaluation. In check, stand pat is not a legal option; an initial mate-range score and evasion generation handle the node.

It probes TT entries with qsearch depth conventions: eval-only entries use -2; ordinary and special qsearch results use -1 or 0. A capture TT move or any suitable evasion TT move can be tried before generation.

Outside check, the generated phase is GP_cap, which includes capture promotions and en passant but not quiet promotion pushes. In check it is GP_evasion. Bad exchanges below seeQThreshold are filtered. Delta pruning can reject near-neutral captures or return beta on sufficiently favorable exchange evidence; doQFutility is currently false.

Past qply 5, non-check nodes can restrict captures to the previous capture's destination when such a recapture square exists. It is not an unconditional capture-depth limit.

Qsearch checks stopFlag, height, mate windows and the post-loop fifty rule; it does not run the full PVS repetition/material recognizer at every entry or perform wall-clock checks itself. Terminal/draw handling is not identical to PVS: no legal evasion establishes mate, but no capture outside check is not a full stalemate test. The auxiliary qsearchNoPruning() is also different: it generates captures even in check and must not be described as the production evasion path.

Draws, mate distances and endgames

PVS's interior recognizer checks repetition, material draws and the pre-loop fifty threshold. isRep() starts four plies back, examines matching-side stack history down to the root, then continues in GameInfo. Captures/pawn moves stop the history walk. It uses a count limit of 2 at PV nodes and 1 otherwise; there is no upcoming-repetition detector.

The fifty rule uses a pre-loop threshold of 101 and a post-loop threshold of 100, allowing the move loop to resolve mate cases first. No legal moves means mate when checked and stalemate otherwise; exclusion searches have distinct no-move behavior.

matingScore(height) = MATE - height and matedScore(height) = -MATE + height. Window clipping implements mate-distance pruning. TT storage converts between root-relative and position-relative mate scores; never treat these values as ordinary centipawns.

Normal drawScore() is a small node-parity-dependent +1/-1, not the configured contempt value. Contempt instead biases evaluation. Armageddon has a different draw mapping.

Syzygy interior WDL probes can return mapped wins/draws; some winning results also incorporate static evaluation as progress guidance. Root probing currently supplies the single selected Fathom root move; commented code for a wider acceptable-move set is not active.

Learning and experimental boundaries

Beta cutoffs reward quiet/capture histories and penalize preceding list entries. TT cutoffs can also update histories. Existing penalties are list-prefix based, not a separately recorded list of exclusively searched moves.

Correction history learns selected non-check, non-mate, non-capture/promotion best results, with reliable-bound gates, against the corrected static baseline. Not every early return learns it.

Adaptive LMR retry depth, correction-magnitude selectivity, NNUE-uncertainty selectivity, continuation correction and upcoming repetition are separate experiments in TODO. None should be inferred merely from an unused field or disabled branch.

Parameterized margins are context-indexed

Coeff<N,M> evaluates:

threshold(d, gp, i, j) =
  ScoreType((init[i] + d*slopeDepth[i] + gp*slopeGamePhase[i])
            * bonus[j] / 256)
active(d, i) = minDepth[i] <= d <= maxDepth[i]

bonus is a multiplier, not an additive centipawn bonus. Depth eligibility and the numerical threshold are separate methods. Index semantics belong to each caller: the common eval-versus-TT/improving interpretation does not apply universally to history/capture-history calls.

For example, static-null margin with i=0, j=0, depth 4 and phase .5 is:

(-15 + 4*82 + .5*149) * 404/256 = 611.5234375 -> 611

The underlying cast truncates rather than rounding to the nearest score. Any modified formula must also respect the narrow ScoreType assertions.

A budget change has more than one effect

IIR changes nominal depth before the ordinary move loop. Pruning gates then use that depth and contextual margins. LMR changes nextDepth, and quiet SEE uses that reduced budget in its threshold. A fail-high can then trigger two different retries. These are successive policies, not one additive "selectivity score".

Do not attribute a changed tree solely to a new LMR coefficient without checking which moves were removed before recursion and how many unreduced retries it caused. Disabled extra reduction/extension predicates likewise need upstream signal and caller-eligibility checks.

For an executable-style specification of all generic reduction/extension switches, TT singular alternatives, clamps, eligibility and retry windows, see the search policy reference.

Move ordering and picking

Why ordering affects more than speed

An early good move raises alpha or cuts off the node before expensive later moves. In Minic, ordering also determines move number, history-pruning evidence and LMR reduction. A move's score can therefore alter which tree is searched, not just the order in which an unchanged tree is visited.

Separate three operations:

generation -> assigning scores -> selecting the next list entry

The PVS TT-first path can avoid the first operation entirely on a cutoff. Once the remaining list is built, partial sorting avoids work on its unused tail, but does not avoid generating that tail.

Score composition

MoveSorter::computeScore() starts from the move-type base in MoveScoring. A nonzero existing score is left unchanged, allowing reuse of ProbCut-scored captures. score() skips lists with fewer than two entries.

Category Base/bonus in the documented source
Ordinary quiet Base 0.
Castling Base 256.
Capture / en passant Base 7000.
Quiet promotions Q/R/B/N Bases 3950 / 3500 / 3350 / 3300.
Capture promotions Q/R/B/N Bases 7950 / 7500 / 7350 / 7300.
Previous best root move Add 15000 at height 0.
TT move Add 14000 if it was not the previous-best case.

The bonuses are additive: there is no single universal score for "the TT move". Active fixed bonuses are search parameters, exposed as UCI options in search-tuning builds: rootBestMoveBonus (15000), ttMoveBonus (14000), recaptureBonus (512), killer0Bonus (1900), killer1Bonus (1300), previousPlyKiller0Bonus (1700, the first killer at height minus two), counterMoveBonus (1500), and threatEscapeBonus (512). Defaults preserve the existing scoring. previousPlyKiller1Bonus (1400) also parameterizes the second killer at height minus two, but that scoring branch remains commented out, so its option has no effect unless the branch is enabled. For example, a TT capture keeps its type base. Source comments that give older bonus values are not the current implementation.

Ordinary captures and en passant

Captures that are not promotions receive a phase-interpolated PST hint: the moving piece's improvement plus the captured piece's removed PST value, divided by capPSTScoreDivisor.

With SEE enabled outside check, add the exchange score and a 512 recapture bonus when applicable. If SEE is below DynamicConfig::badCapLimit, subtract twice the capture base, moving the capture towards the end of the list.

Without SEE, or while in check, add MVV-LVA, recapture and capture-history bonuses instead. Thus capture history is not directly added by this scorer's normal SEE branch, although it is still used for capture pruning/reduction. Promotion ordering uses its own bases rather than this ordinary-capture path.

SEE() estimates successive least-valued captures with x-ray attackers; SEE_GE() currently calls the full SEE() and compares its result with the threshold; it is not a specialized early-exit implementation. Neither substitutes for the legal move application test or a full tactical search.

Killers and counter moves

For ordinary quiets and castling, the scorer takes the first matching branch:

Match Bonus
Current height killer 0 1900
Current height killer 1 1300
Killer 0 at height - 2 1700
Counter to the previous move 1500

These branches bypass generic quiet-history/PST scoring. This is not a strictly descending category ladder: the earlier-side killer's numeric bonus exceeds killer 1, but branch matching still tests killer 1 first.

Killers are two remembered moves per search-relative height. Counter moves map the previous move's from/corrected-to squares to one move identity. The counter-move table is not the continuation-history table.

Generic quiet score

Without a killer/counter match:

score += from/to history / fromToHistoryDivisor
       + piece/to history / pieceToHistoryDivisor
       + pawn-hash/piece/destination history / PawnHistoryDivisor
       + weighted CMH / cmhHistoryDivisor

The three existing divisors and PawnHistoryDivisor currently equal 3. Pawn history uses a 512-entry direct-mapped bucket table keyed by the low bits of Minic's cached p.ph, then colored moved piece and destination square. p.ph includes both kings as well as pawns, unlike pawn-only keys used by some other engines. Its update uses the same depth bonus and bounded gravity as from/to and piece/to histories, with no separate learning-rate scale. Non-castling moves also receive half the PST improvement. This provides a positional prior while learned histories are small.

Pawn history is only included in the generic quiet-history branch; killer and counter moves retain their existing priority and bypass generic quiet history. It is learned through HistoryT::update() for positive beta-cutoff updates and negative updates to earlier quiet moves. Like other histories, it persists between searches and is cleared by game/forced-history resets. The 512 x 13 x 64 ScoreType table costs 832 KiB per worker.

A safe move leaving the square threatened by the null-move refutation can gain 512, provided it is not in check and SEE_GE(..., -80) succeeds. Castling does not use this escape/PST branch. Its destination for histories is the corrected king landing square.

Picking: full sort versus partial sort

With USE_PARTIAL_SORT, pickNext() finds the highest-scored entry in the remaining suffix, swaps it into the selected prefix and advances begin. The implementation uses min_element with a descending comparator; this is why it still selects the largest score.

PVS uses pickNextLazy(), which permanently sets skipSort for that sorter when the previous picked score drops below its threshold, or when the caller says the list is already sorted. Once set, later entries are consumed in their current order. Production qsearch instead calls pickNext() repeatedly without the lazy cutoff; lazySortThresholdQS exists but its use is commented out.

Without partial sorting, the list is fully sorted in descending order. ProbCut separately picks from its capture-only list before the main search adds quiets.

This is not a state machine that generates good captures, quiets and bad captures on demand. Implementing a staged MovePicker would require preserving scoring, legality, duplicate avoidance, list-prefix learning and pruning semantics, not merely replacing pickNextLazy().

History tables and updates

The worker-local tables are:

Table Key
history Side to move, from square, to square.
historyP Colored moved piece, destination.
historyCap Colored moved piece, destination, captured piece kind.
counter_history Context moved piece/destination, current moved piece/destination.

From/to, piece/to and capture history initialize to zero; continuation entries initialize to -1. Killers/counters reset every search, while history tables normally persist through searches in the same game.

getFromToHistory, getPieceToHistory, getCaptureHistory and getPawnHistory provide mutable and const-reference access to entries. Piece indices include color; capture-history victim indices use only the captured piece kind. Destinations are supplied by callers: these accessors do not perform castling correction. CMH continues to use cached row pointers.

The depth bonus and gravity update are:

HSCORE(depth) = 4 * min(depth, 16)^2
bonus        = sign * HSCORE(depth)
boundedBonus = clamp(bonus, -1024, 1024)
item        += boundedBonus - ((item * abs(boundedBonus)) >> HISTORY_POWER)
HISTORY_POWER = 10

The damping scale is HISTORY_MAX = 1024. Capping the depth at 16 keeps HSCORE within that range while preserving the original factor of 4. HISTORY_UPDATE also caps effective bonuses after contextual weighting: CMH ratios can otherwise exceed 1024. The original gravity formula then preserves [-1024,1024] without clamping stored entries, and a zero bonus leaves the entry unchanged. Updates through depth 16 with unscaled bonuses retain the old behavior; larger bonuses now saturate at 1024. This change needs a separate playing-strength comparison.

Quiet history updates require T_std: castling and quiet promotions do not use that update function. Capture history accepts isCaptureNoEP, which includes capture promotions but excludes en passant; caller conditions still matter.

On a quiet beta cutoff, the code updates the killer, counter and positive histories, then applies negative history updates to earlier eligible list entries. Capture cutoffs have their own capture-history updates. TT cutoffs can also learn from their stored move.

Earlier entries are not an explicit record of exclusively searched moves: some can have been skipped/pruned. Changing list layout can therefore change learning as well as search order.

Four-distance continuation history

Current constants:

Prior-move distance Context stack offset Weight
1 Current position's lastMove 8
2 One position slot back 6
4 Three position slots back 4
6 Five position slots back 2

The table row is selected from the colored piece on the prior move's corrected destination in its resulting position. The column is the candidate moved piece and candidate destination.

Distance 1 is the opponent's latest move; distances 2/4/6 are increasingly old moves by the same side as the candidate. Four pointers reference the same counter_history storage; there is no independent distance dimension. Repeated contexts may therefore refer to the same row.

getCMHPtr() checks valid last moves and refuses contexts before rootHalfmoves. A root can still supply distance 1 if its own lastMove is valid; older game contexts are not reconstructed from GameInfo.

The ordering score normalizes only by available weights:

$$ H(m)=\operatorname{trunc}\!\left( \frac{\sum_{i\in I}w_i\,h_i(m)}{\sum_{i\in I}w_i}\right), \qquad (w_1,w_2,w_4,w_6)=(8,6,4,2). $$

\(I\) contains only available context distances, and \(h_i(m)\) is the row's history score for candidate \(m\).

With no context it returns zero. Learning applies a bonus scaled by weight[i] / weight[0] to each available row.

isCMHGood() and isCMHBad() inspect only pointer 0. An absent pointer satisfies neither predicate. Multidistance ordering/learning does not make the pruning test multidistance too.

Worked continuation/history example

Suppose distances 1/2/4 have available entries 320, 100, -80, while distance 6 is unavailable:

weightedCMH = (8*320 + 6*100 + 4*(-80)) / (8+6+4)
            = 2840 / 18 = 157

The absent context contributes neither zero times its weight nor its weight to the denominator. With from/to history 192, piece/to history 96 and PST improvement 30, a generic quiet receives:

192/3 + 96/3 + 157/3 + 30/2 = 64 + 32 + 52 + 15 = 163

This assumes no killer/counter/escape/root bonus. The divisions truncate individually. Summing all numerators before dividing produces a different score in general.

At learning depth 4, HSCORE(4) = 64. Continuation bonuses before damping are 64/48/32/16 for distances 1/2/4/6, respectively. If contexts alias the same row, the actual updates are successive gravity operations on that row, not one update on four independent tables.

SEE algorithm and scope

In searcherSee.cpp, SEE builds attackers to the corrected destination, removes the initial source, updates slider x-rays under a shrinking occupancy mask and alternates least-valued attackers. The stored swap list is folded backward to model declining an unfavorable continuation.

Pawn capture priority changes on a promotion rank; a later pawn capture is treated as queen promotion. Kings are selected only if the remaining attacker set has no opposing piece. Pinned attackers are not filtered by recursively applying each exchange as a fully legal position.

Thus SEE is a local exchange estimate, not a replacement for legality or an oracle for forks/checking sequences. Its initial EP handling has its own special occupancy expression; audit it separately rather than assuming ordinary capture geometry covers EP.

Ordering score as a selectivity input

The move-score value is packed above the 16-bit identity. A root-best or TT bonus changes where a move is picked; killer matching changes whether generic history is even consulted; the same resulting score then feeds quiet LMR, history pruning and bad-capture classification.

For the exact downstream predicates, see the search policy reference. An ordering experiment is not isolated if those consumers retain the old thresholds.

Experimental implications

Keep CMH weights, score normalization and learning scale consistent. Separately test ordering changes and pruning/reduction changes when possible.

Pawn history would be another contextual move-ordering signal, not the existing pawn evaluation cache or pawn correction history. Likewise, continuation correction would learn evaluation residuals, not beta-cutoff move quality.

Score conventions and evaluation data

eval() returns a score for the side to move. HCE accumulates white-positive middlegame/endgame pairs in EvalScore; ScaleScore() combines them:

score = gamePhase * MG + (1 - gamePhase) * endgameScaling * EG

Game phase is high with more material. The material table quantizes phase into an 8-bit value; fallback phase computation derives it from piece/pawn material.

EvalData additionally carries phase, per-color danger, mobility and threat booleans, evalDone, and an uncertainty field. A returned score does not imply every auxiliary field is populated. A cached static score or an early NNUE return can lack HCE attack data; evalFeatures() fills what search needs.

Choosing specialized knowledge, NNUE or HCE

The important selection order is:

variant / terminal special cases
        |
material classification and eligible endgame helpers
        |
NNUE first gate: small enough lazy material score, or force request
        |
full HCE if the first gate did not return NNUE
        |
NNUE second gate: HCE result within a smaller threshold

Bare kings and antichess have early behavior. Recognized low-material positions can use specialized helpers, including KPK, when eligible and not obscured by a legal capture. Material classifications also determine scaling/drawishness. NNUE does not erase those layers.

NNUE requires successful loading and must not be forbidden for the position. The first threshold compares a lazy material-based score against phase-dependent NNUEThreshold/NNUEThresholdEG. The second compares the completed HCE score with NNUEThreshold2/NNUEThreshold2EG.

Runtime forceNNUE overrides the position prohibition in the current expression and the first threshold; the function's force argument bypasses the threshold, not every earlier special case or prohibition. Read both conditions before asserting "forced" means exclusively neural evaluation.

The developer qsearchNoPruning() requests forced NNUE. Production qsearch uses the normal eval() selection; it does not universally force NNUE despite a broader comment in the evaluation API.

The rationale for mixed evaluation is to keep exact/specialized endgame knowledge and avoid some neural work in strongly material-dominated positions, while using NNUE where positional effects can outweigh a lazy material view. The thresholds and score scaling are tuning decisions, not universal constants.

Pawn-and-king cache

Each worker has a direct-mapped cache keyed by pawns and kings. A cache miss constructs pawn attacks, passers, holes, open/semi-open files, structural score and pawn contributions to king danger. King shelter, flank and storm terms explain the king dependency.

Most live tactical geometry remains outside this cache. There is an important exception: cached evalPawnPasser() uses side to move and opposing non-pawn material in its unstoppable test, neither of which is included in the key. Therefore the present entry is not universally a pure function of pawns/kings. For new terms, extend the key or keep those dynamic dependencies outside it.

semiOpenFiles[color] has a repository-specific convention: files containing that color's pawn and no opposing pawn. Do not assume another engine's naming convention.

HCE finalization order

After summing feature groups, the implementation:

  1. Adds sign-aware initiative and context contempt.
  2. Refines endgame scaling for opposite bishops, queen-versus-no-queen and pawn distribution when no earlier specialized scaling applies.
  3. Interpolates MG/EG with phase and endgame scaling.
  4. Applies fifty-move scaling outside Armageddon.
  5. Adds the side-dependent tempo in white-positive coordinates.
  6. Clamps, converts to side-to-move coordinates and applies variant scoring.
  7. Optionally switches to NNUE through the second threshold.

Armageddon suppresses ordinary drawish/fifty scaling in relevant paths and uses variant-specific score shifts. Its draw semantics differ from normal chess.

NNUE features and architecture

Features use 64 king squares, 64 piece squares and 12 colored piece categories: 49152 possible indices per perspective. Both king and piece squares are horizontally flipped unconditionally; black's perspective does not add a vertical flip. Ownership is us/them-relative, and white and black transformers have separate input parameters.

The NNUE reference gives exact indexing examples, matrix layouts, parameter counts, inference equations, update cases and the training/export contract.

The two accumulators each contain 384 values. At propagation they are ordered side-to-move first, concatenated and fed to one of two dense buckets:

white features -> accumulator 384 --\
                                     -> STM-first concat 768
black features -> accumulator 384 --/

fc0: 768 -> 8, activation
fc1:   8 -> 8, activation; concatenate with fc0 -> 16
fc2:  16 -> 8, activation; concatenate with previous 16 -> 24
fc3:  24 -> 1 evaluation
optional fc3_uncertainty: 24 -> 1 log-variance

Bucket 0 is selected for gamePhase < 0.45, bucket 1 otherwise. The active code uses phase, not the commented king-bucket or piece-count alternatives.

The input weights and accumulators are quantized to int16_t at load/inference time with scale 512. Dense layers remain floating point and use clipped ReLU in [0, 1]. SIMD and scalar paths have the same layer topology, including concatenation skip connections. The neural output is multiplied by outFactor = 600.

Do not assume numerical equivalence merely from that topology: the SIMD path clips/dequantizes input activations together, whereas the scalar fallback calls activationInput after dequantizing. That helper's upper bound depends on the quantization scale. Platform comparisons should check actual outputs as well as the dense-layer structure.

Incremental updates

Network weights are shared; each search-stack evaluator owns two accumulators and a dirty state. Initial construction starts from input biases and inserts occupied-square features.

Ordinary moves erase the old piece feature and insert the new one; captures erase the victim. Promotions and en passant need their correct piece/square changes. Moving a king changes its perspective's feature frame and requires a rebuild; the other perspective can still use incremental changes.

Dirty state, explicit reset and evaluator association are part of correctness, not optional performance hints. Propagation asserts a clean evaluator rather than automatically repairing a dirty one. WITH_NNUE_PREFETCH is currently disabled.

Converting a neural output into an engine score

NNUEEVal():

  1. Propagates the selected bucket and converts the evaluation to ScoreType.
  2. Applies phase/endgame scaling to that scalar.
  3. Multiplies by NNUEScaling / 64.
  4. Adds phase-scaled contempt, clamps and applies fifty scaling if appropriate.
  5. Applies variant scoring using absolute ply and explicit search height.

Unlike HCE, it does not add the separate HCE tempo term. The side-to-move accumulator ordering already participates in the learned evaluation.

The uncertainty field is copied from propagation separately; these score transformations do not automatically rescale it.

Contempt is a search-context bias, not an attribute learned by the network. The driver constructs an MG/EG pair from the root side, configured contempt, additional MG contempt and opponent rating factor. A score-dependent dynamic adjustment uses 25 * tanh(previousIterationScore / 400) on its eligible path. Ordinary draw returns still use drawScore(), rather than returning that pair.

File compatibility

Current network version is 0xc0ffee03. Expected file sizes are 151049100 bytes without the optional head and 151049300 with it. A head-disabled build accepts either and ignores the trailing head; a head-enabled build expects the larger format. Filesystem-disabled builds omit the disk file-size check.

The on-disk parameters are floats, quantized during loading. The large input matrices account for most of the file size; the inference representation is smaller. This is Minic's format, not a generic Stockfish NNUE file.

Correction history

Correction history learns systematic evaluation bias from selected search outcomes. It is applied in PVS/qsearch, not baked into network weights:

correction = pawn+king table[side][pawnKey]
           + nonPawn table[side][whiteNonPawnKey]
           + nonPawn table[side][blackNonPawnKey]
correctedStatic = clamp(rawStatic + correction)

The same non-pawn table is queried for both color-specific keys. Each active table has 16384 buckets per side. Mate scores are not shifted.

At learning time:

residual = bestScore - correctedBaseline
change   = clamp(residual * min(depth, 16) / 16, -maximum, +maximum)
item    += change - item * abs(change) / maximum

The pawn maximum is 32; each non-pawn contribution uses 44. With bounded individual table values, the three active contributions can total 120 in magnitude. Hash collisions make this contextual learning, not an exact per-position correction.

PVS learns only under appropriate non-check/non-mate, quiet-result and bound conditions. The optional horizon-context correction table exists but its gate is disabled. Correction magnitude does not currently alter LMR by itself.

Uncertainty: available scaffolding, not active selectivity

WITH_NNUE_UNCERTAINTY is off. Without it, propagation returns a placeholder variance of 1; EvalData::uncertainty is not a calibrated signal.

With the optional head:

variance = exp(clamp(logVariance, -10, 10))

The current Python trainer's uncertainty loss operates on the transformed prediction/target domain. It mixes search-score-derived sigmoid targets and game outcomes; its variable named mse is currently a powered absolute error with exponent 2.4. Do not assume the head already predicts variance in squared engine centipawns or implements a calibrated Gaussian-error model.

Before using it for selectivity, establish meaningful targets, calibration and units; propagate a presence/validity signal through NNUE, HCE and TT paths; then measure a conservative search response.

Correction magnitude is a different signal: learned signed bias is not prediction variance. Both experiments can be interesting independently, but neither guarantees a tactical-safety interpretation. The proposed bounded LMR experiments and eventual combination are described in TODO.

Training and serialization

Train/README.md documents the separate Python/PyTorch pipeline. It is not part of the normal C++ engine build.

train.py loads binary datasets, halfka.py supplies features, and model.py implements the network/loss. serialize.py converts .ckpt/.pt models into the engine's binary parameter order. Training-only factorization must be folded into the exported transformer.

run_games.py and plot.py support candidate evaluation. Compare engine outputs with the exported model; successful loading alone does not prove equivalence.

Time management and parallel search

Two time-management layers

TimeMan::getNextMSecPerMove() converts protocol clock information into an initial allocation. The pool copies it to each worker's currentMoveMs. During search, callers use getCurrentMoveMs(), which applies difficulty, score evolution, variability and caps.

The public inputs include fixed move time, remaining time, increment, moves-to-go/repeating control, processing overhead and node count. targetTime is the nominal allocation; maxTime caps the later adjusted allocation. The distinction is not a guarantee of exact real-time deadlines.

Initial allocation

Control Initial behavior
Fixed nodes Target/max time become effectively infinite; node counting drives stopping.
Fixed move time Target and maximum both equal the requested move time.
XBoard repeating control Average available time and future increments over the remaining moves, with static/dynamic variants.
UCI moves-to-go Divide remaining clock plus expected increments minus margin by moves-to-go.
Sudden death Estimate a remaining-move horizon from risk, game length and game phase, then add an affordable increment contribution.

The dynamic margin is approximately 1% of remaining time, capped at 3000 ms, with moveOverHead as the minimum. UCI/sudden-death allocation has a pondering correction of 1.5 when the relevant pondering state is set.

For sudden death, increment below msecMinimal = 20 is considered risky. The risky horizon remains 28; the non-risky horizon is 16 minus the larger game-length/phase contribution, at most 15. Risky allocation does not rely on increment. Otherwise the increment bonus is capped at 90% of increment and by available clock after the base fraction.

After the dynamic calculations:

targetTime = max(initialAllocation - processingOverhead, 20)
maxTime    = min(remainingClock - margin, 7 * targetTime)

At severe time trouble, minimum-time fallbacks can exceed an otherwise tiny remaining budget. They are best-effort behavior, not a proof against flagging.

Adjusting time during search

With remaining-clock information, getCurrentMoveMs() considers:

Signal Current effect
Forced move Divide allocation by 16.
Easy move Divide by 8; the source notes this category is no longer used.
Iteration-score emergency Multiply by 3, capped at one fifth of remaining clock.
Historical booming Multiply by 1, with the same clock cap.
Historical moobing Multiply by 2, with the same clock cap.

Iteration emergencies take precedence over historical evolution; the factors are not multiplied together. Then variability scales the allocation, maxTime is applied and a final 20 ms floor is imposed.

Consequently, even historical factor 1 can cap an allocation, and the final floor can exceed maxTime in extreme conditions. Do not simplify these rules to "booming always gives extra time" or "maxTime is an absolute deadline".

Within-search instability versus between-search evolution

The driver tracks completed iteration scores. In dynamic timing, beyond depth 14, a decline greater than 64 relative to depth - 2 can switch from standard difficulty to an emergency category. A score above 130 selects the attack-labelled category, otherwise defence.

The IID in these category names refers to iterative-deepening instability; it is not evidence that the disabled traditional internal iterative deepening heuristic runs.

Separately, at a real searched game root, historical evolution compares:

previous = recorded final search score at root ply - 2
former   = recorded final search score at root ply - 4

booming: previous >= former + 80
moobing: previous <= former - 80

These are roots with the same side to move. Missing or mate-range values disable the classification. The prior score selects attack/defence using the same 130 threshold.

The recorded values are final search scores, not pre-root stack evaluations. This restores meaning after the stack began clearing pre-root slots. The old booming expression accepted stable/slightly decreasing scores; the documented working tree requires an actual rise of at least 80.

The main driver consults history only with !subSearch && postMove. The GameInfo chapter explains preservation, validation and publication.

Variability and the next iteration

After depth 12, a score change greater than emergencyMargin / 4 relative to depth - 2 increases variability by a depth-dependent factor; otherwise it decays by 0.98. Its time factor is:

$$ f(v)=\frac{2}{1+\exp(1-v)}=2\,\sigma(v-1), $$

where \(v\) is variability and \(\sigma\) the logistic function.

Variability begins at 1, yielding factor 1. It is a heuristic instability measure, not the NNUE uncertainty field.

The driver estimates effective branching factor from cumulative node counts of consecutive completed depths. Before starting more work, dynamic timing compares:

$$ 1.2\,t_{\mathrm{elapsed}}\,\mathrm{EBF}>T_{\mathrm{allowed}}, $$

with \(T_{\mathrm{allowed}}\) supplied by getCurrentMoveMs().

This is a forecast, not an exact next-iteration duration. In the current order, the stop test precedes recomputation of EBF for the latest depth, so it uses the previously held estimate.

Stop checks and output

timeCheck() is called from PVS on the main worker or a stoppable auxiliary searcher, with a 1024-call countdown. It checks node limits, elapsed time against the adjusted allocation and distributed stopping.

Qsearch checks stopFlag at entry but does not independently sample elapsed wall time. Large qsearch excursions can delay time/node-limit detection. The driver also checks node counts between iterations; depth 1 gets special protection from the requested node cap.

Clock is std::chrono::system_clock, not steady_clock. The current implementation should not be documented as immune to wall-clock adjustments.

For ponder/analysis, the adjusted allocation is effectively infinite. If the search reaches its stopping depth early, the main worker waits for ponderhit or stop before move emission. The protocol operation updates the state/limits; workers are subsequently stopped and joined for that search.

Lazy SMP lifecycle

Each worker has its own position stack, NNUE accumulators, move histories, correction tables and pawn cache. They share the TT and global search settings. Helpers receive effectively unlimited requested depth and rely on stop coordination.

ThreadPool::startSearch():

  1. Waits for the previous main worker.
  2. Updates COM::state late enough not to disturb the previous search.
  3. Sets the atomic start lock and distributes copied ThreadData.
  4. Wakes worker zero, which starts helpers.

Helpers wait on the start lock in the driver before the main iteration loop. Per-worker depth-skipping schedules make the trees diverge. This is Lazy SMP, not deterministic root-move splitting.

At the end, each nonempty PV contributes its completed depth as a vote for its first move. The winning move's deepest supporter supplies the selected ThreadData. This is not simply "take the deepest thread regardless of move". Skill selection can bypass this voting path.

The driver then handles ponder/analysis waiting, stops helpers and waits for them. It records the root search score before final reporting and best-move application. Selection itself occurs before helper stop/wait, so do not imply that every result read happened after all workers became idle.

Synchronization: what exists and what is not guaranteed

Worker wake/wait uses a mutex and condition variable; helper release uses an atomic start lock. GUI command/move operations use COM mutexes, and PV updates have a dedicated mutex.

The implementation also shares ordinary stopFlag booleans and reads worker data during voting. These facts do not establish a complete C++ memory-model proof of race freedom.

The TT is shared without locks or atomic entry storage. XOR validation checks snapshots, but is not formal synchronization. The new game-history mutex protects modifying methods and score getter/setter, not all legacy readers or public fields. Preserve the established lifecycle, and review synchronization explicitly when adding shared state.

Optional distributed search

WITH_MPI is disabled by default. When enabled, rank zero reads commands and distributes input; processes maintain local searches and exchange TT entries, reduce statistics and forward the master's stop state. Dedicated communicators separate input, TT, statistics, moves and stopping.

Nonblocking broadcasts/reductions and a one-sided stop window accommodate divergent trees. Local SMP and MPI can coexist, but they are not the same memory-sharing mechanism. With MPI disabled, the distribution interface mostly becomes no-op plumbing.

Worked sudden-death allocation

Assume remaining clock 60000 ms, increment 500 ms, starting material, absolute ply 1, no pondering, zero processing overhead and configured minimum margin no greater than 600 ms. This is non-risky:

margin = 600
gameLengthContrib = int(min(15, 1/10)) = 0
gamePhaseContrib = int((1-1)*15) = 0
horizon = 16
base = (60000-600)/16 = 3712.5
incrementBonus = min(450, 60000-600-3712.5) = 450
initialAllocation = int(4162.5) = 4162
targetTime = 4162
maxTime = min(59400, 7*4162) = 29134

With variability 1 and no other difficulty, current allowance is 4162 ms. Historical moobing doubles it to 8324; an iteration emergency triples it but the remaining-clock/5 cap yields 12000. A forced-move division yields 260 ms. These categories are selected, not multiplied into one another.

At long game ply the horizon can shrink to 1. The increment-affordability cap then matters: it prevents adding 90% of increment to a base fraction that already consumes the available clock. This is why testing opening roots alone does not characterize late-game timing.

Forecast interpretation

If elapsed time is 500 ms and the held EBF estimate is 2.4, the next-depth test compares 500 * 1.2 * 2.4 = 1440 ms with the adjusted allocation. This uses cumulative elapsed/node history, not an exact measurement of one future iteration. Aspiration retries, TT reuse, changed branching and worker cooperation all make that forecast approximate.

Publication of a new variability/EBF estimate occurs at driver boundaries; PVS periodically checks the current adjusted allowance and qsearch observes the stop flag. Soft forecast, sampled elapsed check and final output latency are three different stopping mechanisms.

SMP result interpretation

Helpers retain local histories and can skip selected nominal depths, yet all consult the shared TT. A fixed-depth request therefore does not imply identical work or an identical trace on every worker.

Final voting is depth weighted, followed by selection of a deep supporting result. Voting reads worker results before the later stop/join sequence, so it must not be described as a snapshot proven synchronized merely by the existence of wait(). Any publication refactor must separately specify result ownership, the happens-before boundary and the score/PV/depth consistency of the selected tuple.

Measuring a timing change

Use both fixed-node/fixed-depth searches and real time controls. The former help isolate tree changes; the latter expose overhead, emergencies, instability and SMP timing. Compare actual move times, overruns, completed depths and historical-score availability, not just nodes per second.

A timing repair can be Elo-neutral while correcting the signal it uses. Only controlled matches can establish its strength effect.

TT layout and indexing

An entry comprises three 32-bit groups:

fingerprint: 32
score s: 16 | evaluation e: 16
move: 16 | bound/flags/generation: 8 | depth: 8

This is normally 12 bytes on the desktop ABI; allocation uses sizeof(Entry), not a hard-coded assumption. The capacity is the largest power of two fitting the requested byte budget:

index = fullHash & (capacity - 1)

The array is aligned to 1024 bytes. There is one entry per index, not a cluster with multiple candidates.

Every store replaces that entry. Depth, generation and exactness do not select a victim. A 3-bit generation advances modulo 8 each search and is stored in flags, but is not currently an aging replacement policy.

hashFull() samples nonzero stored fingerprints and reports per mille. It does not measure the proportion of useful entries from the current generation.

Compressed-key validation

The stored fingerprint is XORed with the two payload words. A read copies the entry and verifies:

storedFingerprint XOR payload1 XOR payload2 == Hash64to32(requestedHash)

A stored valid move is also checked for pseudo-legality in the current position. A mismatch invalidates the returned entry.

getEntry() returns true only when the validated entry has enough depth. A shallower but valid entry can return false while leaving e.h != nullHash; PVS can still use its move/evaluation/context. Distinguish hit from depth-sufficient cutoff candidate.

XOR validation helps reject key mismatches/inconsistent snapshots. It neither eliminates all compressed-key collisions nor makes non-atomic concurrent access formally race-free.

Bounds, flags and mate scores

The bound byte contains upper/lower/exact bound bits, TT-PV, gives-check, in-check and generation flags. Test the relevant bits rather than comparing the entire byte with an unflagged bound constant.

For mate scores, storage adds search height to winning mates and subtracts it from losing mates; retrieval reverses that adjustment. This makes the mate distance reusable from a root with a different height.

TT cutoffs additionally depend on node type, depth, bound direction, mate and fifty-move conditions. Some late cuts allow slightly shallower entries with margins. Excluded-move searches use perturbed keys.

TT::getPV() follows move hints with legality/repetition safeguards. The main search maintains its own PV; this helper is not a promise that every TT chain forms an exact principal variation.

The evaluation-field caveat

The intended distinction is s = search result and e = uncorrected static evaluation. Eval-only writes implement that distinction.

However, several PVS/qsearch cutoff/final writes pass the mutable evalScore, which may already have been replaced by a TT search result. Therefore the current source does not justify the blanket invariant "every stored e is always the raw evaluator output".

Search separately backs up raw staticScore/stack evaluation and avoids deliberately adding correction to a TT search result. If tightening the TT invariant, audit every writer and reader together; changing only the header comment cannot fix the data flow.

Pawn cache

Searcher::initPawnTable() divides the configured total pawn-cache budget by thread count, then rounds each worker's capacity down to a power of two. Entries retain a compressed pawn-and-king key, cached structure bitboards, score and danger. They are direct-mapped and overwritten on a miss.

The default desktop budget is 16 MiB before per-worker rounding; TT defaults to 128 MiB. Actual allocated memory can be lower after power-of-two rounding. Small-memory builds interpret size units differently through SIZE_MULTIPLIER.

The cache stores HCE features, not search bounds or move history. It does not need the side-to-move search key because its stored score is white-positive structural information.

Move and correction tables

See move ordering for indices, weights and update equations. The largest move-history structure is counter_history: a colored piece/destination context by colored piece/destination candidate. Multiple CMH distances use the same storage, so adding pointers is different from multiplying the table by a distance dimension. Their scoring weights are configured by SearchConfig::CMHWeight and exposed as CMHWeight0 through CMHWeight3 when search tuning is enabled; the first weight must remain positive because it normalizes CMH update bonuses. Pawn move history is a separate 512-bucket table per worker, indexed by the low bits of Minic's pawn-and-king hash, colored moved piece and destination. Its 832 KiB per-worker cost is separate from the pawn evaluation cache and pawn correction history.

Correction tables have direct-mapped [side][key & mask] buckets without full-key tags. Collisions intentionally blend observations. The active pawn/non-pawn tables each use 16384 buckets per side; white and black non-pawn keys address the same non-pawn table. Horizon correction has a separate disabled gate.

A correction table learns eval error; a move-history table learns cutoff utility. Their magnitudes cannot be substituted merely because both use ScoreType.

Material and KPK knowledge

The material index encodes piece counts in mixed bases, with separate light/dark-square bishop counts. Precomputation supplies material score, quantized phase, termination classification and optional helper function. Promotion-heavy positions outside the supported count ranges use fallback paths rather than indexing the ordinary table blindly.

The KPK bitbase and specialized helpers are separate from the TT. They supply endgame knowledge determined by a position, not a noisy recent-search cache. Loaded Syzygy files are another independent source with WDL/DTZ and rule-aware mapping.

GameInfo: the actual game

The initial position is stored separately; each subsequent GameStateInfo contains the reached position, move that reached it and optional search score. The initial position has its own optional score.

For a requested absolute ply:

offset = requestedPly - initialPosition.halfmoves
offset 0       -> initial position / initial score
offset 1..size -> states[offset - 1]

The inclusive latest-entry bound is important. A zero search score is a valid observed value; nullopt means no recorded score.

Recording a search result

setSearchScore(p, score) requires:

  1. A recorded position at p.halfmoves.
  2. Matching full position hash.
  3. Matching fifty counter, which the full hash does not encode.

It updates the existing entry; it does not append a searched position. Failure logs a warning instead of silently associating a score with another game/root.

The main driver stores the selected final score only for a real, completed, nonempty-PV result with postMove && !subSearch. Publication occurs after helper stop/wait and before move application. This is the root's search score, not a search of the position after the chosen move.

Skill move selection can choose a move other than the first PV while the recorded score still represents the driver's selected search result; do not generalize it into a freshly evaluated score for every played move.

Rebuilding, branching and undo

UCI reconstructs game moves on position; XBoard uses replay for undo/remove. replace(updated) first compares the initial FENs. If they match, it carries over the initial score and subsequent scores until the first move, hash or fifty-counter mismatch.

This is prefix preservation, not a global "find any identical position and reuse its score" cache. An abandoned branch's future scores are discarded. A supplied midgame FEN establishes a new initial history; positions before it remain unknown.

Starting a new game clears optional scores together with moves. The tests in cli_gameInfoTest.cpp cover zero/missing scores, replay, divergence, FEN origins, rewind, fifty mismatch and reset.

Synchronization scope

The game-history mutex protects clear, append, replace, setSearchScore and getSearchScore. Legacy position/hash/move getters and public members are not independently synchronized. A private temporary GameInfo and the live singleton use the same mutex.

The existing API therefore provides protected score operations, not universal thread-safe access to arbitrary history mutations. Position copies in history also retain non-owning root/evaluator pointers; do not use a historical copy as a fresh incremental NNUE position without proper association/lifetime handling.

Capacity rounding example

With a 12-byte TT entry and requested 128 MiB:

raw capacity = floor(134217728 / 12) = 11184810
rounded capacity = 8388608
payload bytes = 8388608 * 12 = 100663296 = 96 MiB

Consequently configured megabytes are a budget, not a promise of exactly that many allocated payload bytes. sizeof(Entry) and the power-of-two policy determine the actual value; bucket masks rely on that rounding.

The material table has ten ternary counts (white/black knight, light bishop, dark bishop, rook and queen) and two nine-valued pawn counts:

TotalMat = 3^10 * 9^2 = 4782969

It is a deterministic mixed-radix index, not a Zobrist collision cache. Unrepresentable promoted material takes the fallback path. The parallel helper-pointer table also consumes memory; do not estimate startup footprint using only the score-entry array.

Correction-history gravity example

Correction update differs from move-history gravity:

w = min(depth, 16)
change = clamp((bestScore - baselineEval) * w / 16, -maximum, maximum)
item += change - item*abs(change)/maximum

For a pawn-correction bucket at depth 8, residual +20 and old item +8, change = 10, damping is 80/32 = 2 and the new item is 16. With residual -20, damping remains 2 and the new item becomes -4. These integer divisions truncate; they are not the signed right shifts used by move-history damping.

The two non-pawn-key queries reuse one table. Updating both keys does not create two independent learned representations; an alias can receive two updates. Optional horizon correction uses a separate context key and a depth ramp, but is disabled in the normal configuration.

Cache validity versus feature dependency

A correct compressed key says an entry matches the chosen key domain. It does not prove every stored value depends only on that domain. The passer-race dependency discussed in the classical evaluation reference is an example. Similarly, TT e provenance depends on the writer, while GameInfo scores require actual root membership beyond a hash match.

Memory considerations

In addition to shared TT/network/material memory, every worker has a stack, accumulators and histories. The raw two 384-element int16_t accumulators over 2048 slots alone occupy roughly 3 MiB before padding and other stack fields. The continuation table adds over 1 MiB per worker.

The two quantized input matrices occupy about 72 MiB before biases/dense heads; the serialized float matrices are about twice that. Increasing threads does not duplicate those shared weights, but does duplicate local search structures. Use startup size logs and actual process measurements for a specific build.

Coverage checks that a path was exercised, not that its heuristic is beneficial. For invariants, also use the corresponding debug checks with assertions enabled and focused special-move/stack tests.

No single smoke test proves all columns. Perft does not exercise evaluation; an eval comparison does not prove legality; successful protocol parsing does not show that an auxiliary search was excluded from live-game score history.

Designing a diagnostic for a disabled branch

First establish which gate prevents execution: compile-time feature, local constexpr switch, runtime option, node type, depth, or producer signal. Then assert its exact intended consequence, such as next depth and retry count, on a deliberately qualifying position.

A disabled emergency modifier with a producer fixed false needs a producer experiment too. An advanced-pawn modifier behind an advanced-pawn exclusion needs an eligibility decision. Simply flipping every named switch obscures these distinctions.

For numerical NNUE checks, include both buckets, both sides to move, feature orientation, export order, quantization range, scalar/SIMD differences and king-frame resets. This is a compatibility experiment before it is an Elo experiment.

Do not put a runtime setting in config.hpp, or scatter a tunable margin across multiple source files. Conversely, a compiled-out feature cannot be enabled by merely adding a UCI option.

Correctness, speed and strength are separate

Correctness: legal state transitions and lines, stable invariants, proper stop/error handling and score/history semantics.

Performance: time per operation, nodes per second, memory traffic, allocation overhead and SMP scaling.

Strength: quality of selected moves under the target limits, measured with controlled games or suitable statistical tests.

A stack-safety repair can be Elo-neutral; fewer nodes can be a bad pruning change; lower NPS can be a better tree. Do not use one metric as proof of the other.

For search experiments, compare fixed-node/fixed-depth results first, then matched real time controls with the same network, options, hardware and opening policy. Preserve baseline binaries and record thread/hash/pondering settings. Separate correctness regressions from measured Elo results.

Safe change checklist

Before publishing a change, inspect existing patterns and all dependent state, use the smallest relevant diagnostics, then broaden coverage where the change touches shared invariants. Keep unrelated fixes out of the experiment.

Update this guide when changing enabled heuristics, equations, state ownership, reset behavior or file compatibility. Update TODO separately for unimplemented ideas; do not silently turn an experimental proposal into a description of the current engine.

Search and bounds

Details: search.

Term Meaning
Node One searched position/context. Same-board exclusion or verification searches can create different contexts for that board.
Edge Move connecting a parent search position to a child.
Negamax Minimax written using side-to-move scores: a parent's move score is the negative of its child's returned score.
Alpha / beta Lower and upper endpoints of the current search window; not material values or move-ordering ranks.
Alpha-beta Search that omits work once the window proves it irrelevant to the parent's choice, subject to any selective approximations.
Window Interval supplied to a search. The implementation's comparisons, not a drawing's endpoint notation, define boundary behavior.
Null window / zero window Integer-score window of width one, commonly [alpha, alpha+1]; despite the name its numeric width is not zero.
Fail-low Result at or below the original alpha; an upper-bound outcome.
Fail-high Result at or above beta; a lower-bound outcome and potential cutoff.
Exact bound Result inside the searched window. In a selective engine it is not proof of exhaustive game-theoretic minimax.
Upper / lower bound Search evidence that the score is at most / at least a stored value, subject to the searched context.
Fail-soft Returning a value outside the original window rather than only its boundary. Always retain the matching bound interpretation.
Beta cutoff An adequate move reaches beta and stops the remaining move loop.
Alpha update A move raises the best score above alpha; it need not cause a cutoff.
Principal variation / PV Best line currently maintained by the search; incomplete/retried lines are not necessarily the final reported line.
PV node Minic's PV template specialization, normally associated with full-window work and PV maintenance.
Cut node A hint that a cutoff is expected. It is predictive context, not a property proved before search.
All node Traditional expected node where every move must fail low; do not infer a separate Minic specialization from this generic term.
TT-PV / former PV Context derived from the current PV flag and TT metadata, used for prudence; not a guarantee the old line remains best.
PVS Principal Variation Search: search an early move normally, challenge later moves with a narrow window, then retry promising results.
Re-search / retry Another search attempt with a different depth, window or cut-node hint; distinguish which quantity changed.
Iterative deepening Search successive root depths, retaining completed results and ordering/timing information between iterations.
Aspiration window Initially narrow root window around an earlier score; fail-low/high causes widened retries.
MultiPV Multiple root variations requested for output. Additional root work is not identical to one ordinary best-line search.
Quiescence / qsearch Search beyond the main depth horizon to reduce tactical instability. Minic searches evasions when checked and captures otherwise.
Stand pat Static score used as a qsearch baseline when not in check. It is not literally a legal pass move.
Horizon effect Apparent safety caused by a consequential event lying beyond the explored budget.
Terminal node Position where search returns without ordinary continuation, for example mate, draw or another early recognized ending.
Mate-distance score Reserved score near MATE, adjusted by relative height to favor shorter wins and delay losses.
STOPSCORE Internal stop sentinel; not a valid ordinary evaluation to publish as centipawns.
Root result Selected move/score/PV/depth tuple for reporting, potentially selected through worker voting.
Completed iteration Finished root-depth result; distinguish it from partially searched or failed aspiration attempts.

The negamax relationship, abstracting the engine's selective policies, is:

$$ V(p,d)=\max_{m\in\mathcal{M}_{\mathrm{legal}}(p)} \left[-V(p_m,d-1)\right]. $$

This notation does not claim that Minic visits every legal move at depth \(d\).

Neural evaluation and training

Details: NNUE reference.

Term Meaning
NNUE Efficiently updatable neural evaluation: maintain sparse-input affine sums incrementally, then run the dense head.
HalfKA King-conditioned, all-piece feature family including kings. Match Minic's actual mapping, not another engine's similarly named layout.
Perspective One side's king and us/them ownership convention. White/black have separate learned input matrices.
Feature index Encodes king square, piece kind/ownership and piece square; 49152 possibilities per perspective.
Active feature An occupied piece-square conjunction in the current king frame; inactive features contribute zero.
Sparse input Store/process occupied feature indices instead of multiplying a dense 49152-element input at each node.
Transformer Input affine layer, forming 384 sums for each perspective from active feature rows and biases.
Accumulator Per-position vector of those sums. This is local state, not the shared matrix of network weights.
Bias Learned additive parameter independent of current input; initializes an affine sum.
Incremental update Erase/add feature rows when pieces change, preserving the unchanged affine contributions.
Reset / rebuild Reinitialize from biases and all active features, needed when a perspective's king frame changes.
Dirty evaluator Validity marker requiring explicit update/reset; propagation asserts clean state, rather than generally repairing it automatically.
STM-first concatenation Put the side-to-move accumulator first, then the other perspective; null moves change this order without changing board features.
Dense layer Affine matrix/bias computation using all values of the preceding vector.
Clipped ReLU Activation bounded between 0 and 1 in the normal dense/SIMD input path; scalar input clipping has a documented difference.
Linear head Final affine scalar without clipped activation, producing evaluation or log variance.
Skip connection Earlier values bypass an intermediate transformation. Minic uses concatenation, not residual addition.
Bucket One of two phase-selected dense parameter sets; not a king bucket or piece-count bin in the active inference path.
Tensor shape Number/order of dimensions. Actual dense inputs are 768, 8, 16 and 24, not merely repeated 8-wide layers.
Quantization Convert input floats to rounded int16 weights/biases with scale 512; dense parameters remain floats.
Dequantization Convert int16 sums to float using reciprocal scale before neural activation.
Saturation / clipping Restrict a value's range. Per-weight load clipping does not prove all accumulator sums remain in int16 range.
SIMD Single Instruction Multiple Data execution; instruction set, layout and reduction order can change rounding and throughput.
Alignment Storage address boundary needed by selected vector loads/stores; NNUE uses 64-byte alignment.
FMA Fused multiply-add with one rounding step; can differ numerically from separate multiply and add.
Transposed weight layout Loader converts disk input-major dense weights to output-major rows for SIMD dot products.
Factorizer Training-only shared piece-position component folded into king-conditioned weights at export.
Export / serialization Write parameters/version in the loader's required layer/bucket ordering and numeric format.
Embedded network Network bytes included in the executable; distinct from loading an external runtime file.
Inference Evaluation using fixed loaded weights; it does not perform online backpropagation in the search.
Target Desired training output, currently blending score-derived probability and game outcome by lambda.
Outcome Win/draw/loss label mapped to a probability-like target; orientation must match the training loader.
Powered error Training uses absolute sigmoid-target error to power 2.4, not ordinary squared error.
Sample weighting Adjust each training example's contribution; active surprise weighting differs from the calculated but unused zone weights.
Dropout Training regularization that randomly suppresses activations; the model's dropout calls are commented out.
Log variance Optional head output transformed by exponential after clipping; not already a standard deviation.
Variance / standard deviation Usually dispersion and its square root. Minic's optional training target is not automatically calibrated in engine-score units.
Uncertainty head Optional additional neural output; disabled in the normal C++ build and not currently a search selectivity signal.
Calibration Empirically checking that predicted confidence/dispersion matches observed error in a specified domain.
Correction versus uncertainty Correction estimates signed bias; uncertainty concerns dispersion/error risk. Their magnitudes are not interchangeable.

Search policy reference

Index | Search overview

This chapter specifies the actual depth arithmetic, eligibility predicates and disabled alternatives. The main implementation is searcherPVS.hpp, with parameters in searchConfig.cpp and precomputed tables in searchConfig.hpp. All statuses refer to the documented snapshot, not a recommendation to enable every available branch.

Coordinates and arithmetic

Use these symbols:

d   remaining depth at this point in PVS, after any IIR
h   relative search height
n   validMoveCount, including legal moves later pruned
q   validQuietMoveCount, counting ordinary quiet candidates
E   this move's extension, possibly negative in the singular TT path
R   this move's reduction
X   cumulative extensions argument passed down the line
s   Move2Score(move), an ordering score, not a searched position score
v   evalScore, possibly substituted by a TT search score
g   game phase in [0, 1]

An ordinary child receives d - 1 + E - R and h + 1. Exclusion and verification searches can recurse on the same position, so absolute game ply need not advance along with their height argument.

DepthType is signed 8-bit. Arithmetic is frequently promoted to int before the final conversion. A new term must respect both the resulting depth range and the cumulative-extension range; a valid-looking expression can overflow a narrow result if inserted before the existing guards.

Three move-search paths

Path Budget and conditions
TT move Tried separately before ordinary generation; child depth d - 1 + singularExtension. Does not pass through generic LMR.
First eligible generated move validMoveCount < 2, or PVS globally disabled; full window and depthPolicy(..., false). Generic extensions could apply, but LMR does not.
Later generated move Pruning gates first, then depthPolicy(..., isReductible), reduced null window, possible unreduced and full-window retries.

An already tried TT move is skipped in the generated list. A rejected illegal candidate does not increment the legal count; a legal but pruned candidate does. Thus the LMR table's move index is not simply "number of recursive calls already made".

The later-move predicates are:

isPrunable =
    !advancedPawnPush && !mateScore(alpha)
    && !currentHeightKiller && !mateFinder

isReductible =
    doLMR && d >= lmrMinDepth
    && !advancedPawnPush && !mateFinder

These are intentionally different. A killer is protected from these pruning branches, but that does not by itself exempt it from LMR. The current advanced-pawn test is based on piece kind and destination rank < 2 or > 5; it is not a passed-pawn test.

isQuiet currently means T_std && !isNoisy(), and isNoisy() merely tests whether the type is not T_std. Commented pawn/knight fork detection is not active. Promotions, castling and EP are not ordinary quiets by this definition.

Base LMR table

For positive depth/move indices:

$$ L(d,n)=\operatorname{trunc}\!\left(0.4\,\ell(1.6d)\,\ell(n)\right), \qquad \ell(x)=\operatorname{my\_log2}(x)\simeq\ln(x). $$

The helper computes an approximation of the natural logarithm, despite its name. It repeatedly halves x into a smaller interval, uses the odd-power series with y = (x - 1) / (x + 1), then adds the removed multiples of ln(2). Replacing it with std::log2() would change the table, not merely optimize it.

Indices are capped at MAX_DEPTH - 1 and MAX_MOVE - 1. The table's zero row/column remains zero. It is calculated once, not recalculated per move.

Algorithmic motivation: depth makes shallow inspection affordable and later move rank suggests lower probability of improving alpha. Both are heuristic priors; reduced fail-lows can still hide good moves.

Active ordinary-quiet reduction terms

Only T_std enters this branch:

R = L[d][n]
  + !improving
  + ttMoveIsCapture
  + likelyFailHigh
  - min(3, HISTORY_DIV(2 * s))
  - (formerPV || ttPV)
  - knownEndgame

likelyFailHigh is true when this is a cut node and:

v - failHighReductionCoeff.threshold(marginDepth, g,
                                    evalScoreIsHashScore, improving) > beta

This particular term consumes evalScore, not a newly recomputed corrected static value. marginDepth is reduced by usable TT depth when the static estimate was replaced by a TT search result.

HISTORY_DIV(x) is an arithmetic right shift by 10. Its negative-value behavior matters: score -100 gives (-200 >> 10) == -1, while score +100 gives zero. Subtracting that negative value increases reduction. The positive side is capped at 3; this expression has no corresponding explicit -3 clamp.

The input s is the whole ordering score. Killer/counter bonuses, PST hints and escape bonuses can participate; "history reduction" is not limited to one raw history table.

ttPV includes the current PV-node flag as well as eligible TT-PV metadata. Consequently the enabled former-PV prudence already protects ordinary PV nodes, even though the separate enableReduceLessAtPVNode switch is false.

Worked quiet example

At depth 8 with the eighth legal candidate, the base is approximately 2. For not-improving, a capture TT hint and a likely fail-high, add 3. An ordering score of 1100 gives history adjustment 2; TT-PV context removes another 1. Without known-endgame prudence:

R = 2 + 1 + 1 + 1 - 2 - 1 = 2
nextDepth = 8 - 1 - 2 = 5

If the reduced score exceeds alpha, the retry returns to depth 7. This example assumes the candidate passed pruning and no extension applies; it is not an Elo argument for any coefficient.

Active ordinary-capture reduction terms

Only T_capture, not EP or capture promotion, enters this branch:

R = L[d][n]
  - clamp(HISTORY_DIV(9 * captureHistory), -2, 2)
  + (badCapture && R_after_history > 1)
  - pvnode
  - improving

Capture history is indexed by the colored source piece, destination and captured piece kind in the parent position. The bad-capture increment is evaluated after the history adjustment, before PV/improving deductions. Changing this order changes behavior.

For other move types the branch leaves R = 0, although generic normalization still applies when the caller marked the move reducible. Do not infer an EP or promotion LMR policy from the presence of isCapture() elsewhere.

Generic normalization and retries

For reducible moves, two adjustments constrain the initial result:

if E - R > 0:
    R = E
if d - 1 + E - R <= 0:
    R = d - 1 + E
nextDepth = d - 1 + E - R

Thus this path cannot create a net extension and cannot reduce below depth zero. A first generated move, passed as non-reducible, bypasses those adjustments; a hypothetical enabled generic extension could survive there.

The resulting budgets, after those adjustments, are:

$$ d_{\mathrm{child}}=d-1+E-R,\qquad d_{\mathrm{unreduced}}=d-1+E. $$

Later search uses:

reduced:   -pvs<false>(-alpha-1, -alpha, child, nextDepth, cutNode=true)
retry:     -pvs<false>(-alpha-1, -alpha, child, d-1+E, cutNode=!parentCutNode)
PV retry:  -pvs<true> (-beta, -alpha, child, d-1+E, cutNode=false)

The unreduced retry requires R > 0 && score > alpha. The PV retry requires score > alpha && (rootnode || score < beta). Cut-node hints can therefore change between attempts. Child PV storage is cleared between retries.

flowchart TD
    Start["Later legal candidate"] --> Prune{"Pruning gate triggers?"}
    Prune -->|yes| Skip["Skip candidate / possibly mark tail"]

Experiment discipline

Enabling a switch is not enough if its upstream signal is forced zero, its caller excludes every eligible move, or another enabled term duplicates it. Record candidate/search/prune counts separately; compare reduction histograms, retry frequency and exact selected depths under fixed-node tests.

A safe experiment also preserves score-domain separation, excluded-key semantics, narrow-type limits and same-position stack ownership. Use match testing for strength conclusions rather than assuming deeper search is better.

Kings are not part of the ordinary phase numerator/denominator. This separation prevents a SEE tuning change from silently being treated as a material-eval or phase tuning change.

Fallback phase is remaining pawn/piece phase-weight sum divided by the starting army total, capped at 1. A normal material-table hit supplies phase as an 8-bit quantized fraction and a precomputed white-minus-black score.

The material score includes second-degree imbalance from material.cpp:

imbalance(c) =
  sum over m1 and m2 <= m1:
    ownCoeff[m1][m2] * ownCount[m1] * ownCount[m2]
  + opponentCoeff[m1][m2] * ownCount[m1] * opponentCount[m2]
  all divided by 16, separately for MG and EG

The table subtracts black's imbalance from white's. In an eval-tuning build these precomputed imbalance contributions are set to zero; the out-of-table material fallback also does not reproduce that polynomial. These are real path differences.

Evaluation construction order

HCE starts with material, then builds non-pawn PST/attack information, obtains pawn/king cached terms, derives attack quality and dynamic pawn/piece features, adds mobility and remaining placement/material corrections, applies style, initiative, contempt and final scaling.

The order is dependency-driven: safe mobility needs both sides' attacks; outposts need pawn holes and defenders; nonlinear king attack needs raw danger; endgame scaling needs the strong side and passer counts.

Seven feature groups retain white-positive MG/EG pairs:

material | positional | development | mobility
attack   | pawnStruct | complexity

EvalData contains selected persistent summaries; the local feature groups do not survive the call. Search-side evalFeatures() is not the complete HCE.

Attack-map construction

For each non-pawn piece, compute two coverages:

shadow = coverage(square, occupancy XOR ownNonPawnOccupancy)
actual = coverage(square, occupancy)

The shadow board removes own non-pawn blockers, including the king, to estimate aligned pressure into the opposing king zone. Actual attacks preserve the real occupancy and populate:

Name Meaning
att[c] Union of attacks.
att2[c] Squares reached by overlapping attack sets.
attFromPiece[c][kind] Union for a particular attacking kind.
checkers[c][kind] Source squares of pieces actually attacking the enemy king.

Before merging a new actual set T, att2 |= att & T, then att |= T. Pawn targets from the cache later join att/att2.

The current HCE loop begins at knight, not pawn. It merges pawn attacks into aggregate maps and fills pawn checker sources, but does not populate the pawn row of attFromPiece in this path. The search-side reconstruction loops over pawns too. Therefore their goodThreats construction must not be assumed identical merely because the final formula has the same spelling.

Weak, safe and protected squares

Let A[c] and A2[c] denote aggregate and double attacks, and K[c], Q[c] the king/queen attack maps. For one side:

weak[c] = A[opponent] & ~A2[c] & (~A[c] | K[c] | Q[c])
safe[c] = ~A[opponent] | (weak[opponent] & A2[c])
protected[c] =
    pawnTargets[c]
  | (A[c] & ~A[opponent])
  | (A2[c] & ~A2[opponent])

These are tactical approximations, not proof that a king move or capture is legal. A square defended only by a high-value piece can remain weak; multiple favorable attackers can make a contested square count as safe.

haveThreats[c] tests attacks on any opposing piece. goodThreats[c] emphasizes pawn attacks on non-pawns, minor attacks on rooks/queens and rook attacks on queens. It is not computed using SEE for every threatened target.

King safety: raw pressure to MG score

Raw kdanger combines shadow attacks on the enemy king zone, actual defense of one's own zone, cached pawn/flank effects and safe-check rewards. Attack weights are (125, 189, 251, 153, 153, -39) for pawn through king; defense weights are (41, 100, 96, 48, 26, 0).

Safe-check weights are (122, 785, 569, 934, 776, 0). They apply to checker source squares intersected with the relevant protection/safe set; this is a reward for existing checker geometry, not generation of every possible future checking move.

Absence of an opposing queen subtracts 585 from danger. The nonlinear table is:

$$ \begin{aligned} i &= \operatorname{clip}\!\left(\operatorname{trunc}(D/32),0,63\right),\\ K(i) &= \operatorname{trunc}\!\left( \frac{492}{1+\exp((35-i)/11)}-5\right). \end{aligned} $$

\(D\) is raw king danger, and \(K(i)\) is the integer table value. Both casts truncate toward zero rather than applying a mathematical floor.

White's table value is subtracted from white-positive MG attack score; black's is added. EG gets zero from this conversion. Raw danger, rather than the nonlinear score, is also exposed to search.

The sigmoid saturates high pressure and avoids an unbounded linear penalty. Integer division, index clipping and conversion can create small plateaus; threshold consumers should not pretend the final score is continuous.

Threat and mobility features

Hanging pieces are own non-pawns on weak squares, with pair (-29, -18). Minor-piece threats target opposing non-pawns or weak pawns; rook/queen/king threats use weak opposing squares and victim-kind-indexed tables.

Rooks, queens, pins and material refinements

Rook open-file pair is (41, 24); the two semi-open classes use (24, -2) and (28, 17). Queen/rook file alignment uses (-1, 35). Facing enemy rooks are tested with front-span geometry, not a full legal exchange calculation. Queen proximity uses 7 - ChebyshevDistance to the enemy king and coefficient (10, 6).

King/queen pin terms use a helper that identifies opposing sliding pinners with selected occupancy and intersects own pieces along rays. The present helper's final between() call uses p.king[c] even when called with a queen square. Describe these as implemented pin features, not a general-purpose exact pinned-to-arbitrary-square API.

Queen-square terms select the first queen in the bitboard; the source itself notes the multi-queen limitation. Pawn-count-dependent knight/rook adjustments, same-square-color bishop pawn penalties and pair adjustments then refine material. Pair "malus" names also do not guarantee negative tuned coefficients: the knight pair is (14, -7), rook pair (58, -30).

Style, initiative and final scaling

The ordinary style multipliers affect MG only:

MGgroup *= 1 + (style - 50) / 50
EGgroup *= 1

Complexity instead uses (styleComplexity - 50)/50 for MG and zero for EG. At default 50 its contribution is zero, even though a raw side-to-move piece/pawn-count complexity term was calculated.

Initiative is computed after summation from pawn count, pawns on both flanks, a pawn-only ending flag and an offset:

rawInitiative =
    (-1, 6) * totalPawnCount
  + (70, 43) * pawnsOnBothFlanks
  + (115, 65) * exactlyTwoNonPawnOccupiedSquares
  - (59, 83)

In ordinary chess the last boolean recognizes kings and pawns only. Each phase then uses:

initiative = sign(score) * max(rawInitiative, -abs(score))

This prevents the initiative adjustment alone from reversing that phase's sign, while permitting either amplification or contraction. Contempt follows.

When no prior material scaling applies and Armageddon is off, the strong side is white if the current EG score is positive and black otherwise. EG scale is:

First qualifying case Scale
Opposite bishops, no other non-pawns (34 + 20*strongSidePassedPawnCount)/128.
Opposite bishops with other material (80 + popcount(strongSideOccupancy))/128; occupancy includes pawns and king.
Exactly one queen on the whole board (79 + 0*queenlessSideMinorCount)/128, currently constant.
Otherwise min(1, (75 + 25*strongSidePawnCount)/128).

If pawns exist on only one flank, subtract the one-flank term afterwards. Its coefficient is -20, so this increases the scale by 20/128; it is not necessarily capped back to 1. A comment saying "scale down" is not the actual arithmetic.

Phase interpolation is:

$$ S=\operatorname{trunc}\!\left( g\,S_{\mathrm{MG}}+(1-g)\,s_{\mathrm{EG}}\,S_{\mathrm{EG}}\right). $$

\(g\) is game phase and \(s_{\mathrm{EG}}\) the specialized endgame scale.

Only EG is multiplied by this specialized scaling. For MG 100, EG 200, phase .25 and EG scale .5, the fused score is 100, not 125 or 175.

Fifty scaling in score.hpp is 1 - fifty^2 / 10000, not a linear fade. At counts 50/80/90 the factors are .75/.36/.19. HCE applies this before tempo 15; NNUE adds contempt before its own fifty scaling and has no separate tempo. Those orders are observable.

Endgame knowledge and scope

With fewer than five total non-pawns and eligible material classification, evaluation checks for an actual legal generated capture before using helpers. KXK pushes the weaker king to edges and brings kings closer; KmmK uses corner geometry; KPK probes the normalized bitbase. KBPK can approximate a wrong-color bishop ending using KPK knowledge.

These helpers are not Syzygy DTZ, nor a complete replacement for mate/stalemate search. Material-table classifications can amplify or suppress EG scaling without claiming an exact win proof.

When adding a feature, specify its score group, orientation, cache dependency, MG/EG meaning, style interaction, narrow-type range and whether search consumes its auxiliary data. A term's intuitive chess label is only the starting point.

What an input feature means

For a given perspective, a feature is a conjunction of:

that perspective's king square
piece square
piece kind
whether the piece belongs to the perspective or its opponent

There are 64 * (12 * 64) = 49152 indices. FeatureIdx::major = 768 is the stride per king square; minor = 64 is the stride per colored piece kind. Offsets are pawn/knight/bishop/rook/queen/king for us, then those six for them. Both kings are included as occupied-square features.

The current index expression is:

indexUs(k, s, p)   = 768 * HFlip(k) + HFlip(s) + usOffset(p)
indexThem(k, s, p) = 768 * HFlip(k) + HFlip(s) + themOffset(p)
HFlip(square)     = square XOR 7
getBlock(square)  = square

The horizontal flip is unconditional. It is not king-file-dependent symmetry reduction, and there is no black-perspective vertical flip in this expression. Color-relative ownership and separate transformer parameters provide the perspective distinction. Do not substitute a conventional HalfKA orientation from another engine.

An alternative 16-block expression is commented in getBlock(); it is not the active 64-square layout. The sparse C++ training loader duplicates the active expression; changing it requires synchronized feature/export changes.

Concrete index

For white king e1 (4) and a white pawn e2 (12):

HFlip(e1) = d1 = 3
HFlip(e2) = d2 = 11
white-us-pawn index = 768*3 + 11 + 0 = 2315

If black's king is e8 (60), its perspective treats that pawn as "them":

black-them-pawn index = 768*59 + 11 + 384 = 45707

These access different matrices and rows. "Both perspectives see the same piece" does not imply they use the same learned weights.

Sparse affine transformers

For perspective c and accumulator component j:

$$ A_{c,j}=b_{c,j}+\sum_{i\in\mathcal{F}_c}W_{c,i,j}, \qquad j\in\{0,\ldots,383\}. $$

Here \(\mathcal{F}_c\) is the set of active features for perspective \(c\); \(W_{c,i,j}\) and \(b_{c,j}\) are stored input weights and biases.

Inactive input features are zero; there is no dense 49152-vector multiplication at every position. Reset copies 384 biases and inserts one 384-row per occupied square. There are two parameter sets, weights.w and weights.b, not one shared transformer reused with only a color flip.

The model learns a king-conditioned linear summary; nonlinearity occurs when the resulting accumulators are activated. Incremental updates are possible because removing/adding a feature is subtracting/adding its row.

Exact dense topology

Let clip(x) = min(max(x, 0), 1). In the normal SIMD path:

u = clip(A[sideToMove] / 512)
t = clip(A[opponent]   / 512)
x = concat(u, t)                              # 768

y0 = clip(W0*x + b0)                          # 8
z1 = clip(W1*y0 + b1)                         # 8
y1 = concat(y0, z1)                          # 16
z2 = clip(W2*y1 + b2)                         # 8
y2 = concat(y1, z2)                          # 24
evaluation = 600 * (W3*y2 + b3)               # 1
optional logVariance = Wvariance*y2 + bvariance

The final scalar is not clipped with ReLU. The skip connections are concatenations, not residual sums. Earlier activated values remain directly available to later layers and the output.

With \(\phi(v)=\operatorname{clip}(v,0,1)\) applied componentwise, the dense relationships are:

$$ \begin{aligned} y_0 &= \phi(W_0x+b_0),\\ y_1 &= [\,y_0;\ \phi(W_1y_0+b_1)\,],\\ y_2 &= [\,y_1;\ \phi(W_2y_1+b_2)\,],\\ e &= 600\,(W_3y_2+b_3). \end{aligned} $$

The semicolon denotes concatenation. The diagram makes the different input widths and bypass paths explicit:

Quantization and numerical limits

Disk parameters are floats. Input rows/biases become round(floatValue * 512) in signed 16-bit storage. The loader logs and clamps out-of-range individual weights/biases.

With input scale \(q=512\), the normal SIMD path can be summarized as:

$$ \begin{aligned} \widehat W_{c,i,j} &= \operatorname{round}(q W_{c,i,j}),\\ \widehat b_{c,j} &= \operatorname{round}(q b_{c,j}),\\ \widehat A_{c,j} &= \widehat b_{c,j} + \sum_{i\in\mathcal F_c}\widehat W_{c,i,j},\\ x_{c,j} &= \operatorname{clip}(\widehat A_{c,j}/q,0,1). \end{aligned} $$

The stored accumulator is the unclipped sum. Clipping its stored value after each insertion would lose information and invalidate later erase/add updates. Activation belongs to propagation.

If all parameters fit without load-time clamping and no accumulator overflows, rounding gives the per-component preactivation error bound:

$$ \left|\widehat A_{c,j}/q-A_{c,j}\right| \leq \frac{|\mathcal F_c|+1}{2q}. $$

For 32 active features, this is \(33/1024 \simeq 0.03223\) before dense inference. It is not a centipawn-error guarantee: the dense weights, subsequent activations and output scale determine how the error propagates.

That per-parameter check does not prove every sum of active rows fits int16. StackVector incremental operations do not add an explicit accumulator saturation policy. Training/export must preserve reasonable ranges, and reset versus incremental comparisons should include crowded/material-unusual boards.

Dense weights and biases remain float; this is not a fully integer NNUE. Accumulator dequantization, dense matrix multiplication and clipping therefore have different numerical characteristics.

NNUEALIGNMENT is 64 bytes. StackVector and matrix/bias arrays use aligned storage. SIMD input conversion widens int16 values, multiplies by 1/512 and clamps to [0,1], with vector and tail loops. Dense dot products exploit architecture-dependent SIMD; exact rounding need not be bit-identical across compiler/ISA/FMA settings.

Historical fully integer formulation

The former standalone quantization note described a different design: integer dense weights/activations and wider integer biases/dot products. Its reasoning is preserved here as a historical design reference, not as a description of the currently enabled mixed int16/float network.

Start from a floating hidden layer \(y_i=\operatorname{clip}(W_i y_{i-1}+b_i,0,1)\). Assume a weight bound \(|W_i|<\alpha\), choose an integer activation range \([0,n]\), and define \(f=n/\alpha\). Let \(Q\) convert a scaled real value to an integer. The original derivation used floor; the current input loader uses rounding. These quantizers have different error and negative-value behavior.

For binary sparse input \(x\), quantize the first affine layer at scale \(n\):

$$ \begin{aligned} \overline W_0 &= Q(n W_0), & \overline b_0 &= Q(n b_0),\\ a_0 &= \overline W_0x+\overline b_0, & z_0 &= \operatorname{clip}(a_0,0,n)\simeq n y_0. \end{aligned} $$

Input weights can exceed int8 even when subsequent dense weights fit it; the historical proposal therefore used int16 for input rows. Input accumulator width must still be justified from the unclipped sum, not from the bounded range of \(z_0\).

To preserve \(z_{i-1}\simeq n y_{i-1}\) in an integer hidden layer:

$$ \begin{aligned} \overline W_i &= Q(f W_i),\\ \overline b_i &= Q(n f b_i)=Q(n^2 b_i/\alpha),\\ u_i &= \overline W_i z_{i-1}+\overline b_i,\\ z_i &= \operatorname{clip}(u_i/f,0,n)\simeq n y_i. \end{aligned} $$

The bias needs scale \(n f\), not merely \(f\), because the dot product multiplies weights scaled by \(f\) with activations scaled by \(n\). The original proposal used int8/int16 dense weights with int32 biases and computation results. A concrete implementation would also have to define the rounding of \(u_i/f\), overflow handling and integer clipping; these equations do not supply those implementation details.

The output head is linear, so it omits clipped ReLU. If the integer dot product is \(\overline o\simeq n f o\), restore the evaluation scale using:

$$ 600\,o \simeq \frac{600\,\overline o}{n f} =\frac{\overline o}{s}, \qquad s=\frac{n f}{600}=\frac{n^2}{600\alpha}. $$

Here \(s\) is the historical integer output divisor. It is not the current input dequantization factor \(1/512\): today's float head simply multiplies its output by 600.

Historical choice \(n\) \(\alpha\) Exact \(f=n/\alpha\) Bias scale \(n f\) Output divisor \(s\)
Int8 dense weights 127 2 63.5 8064.5 About 13.44.
Int16 dense weights 1024 4 256 262144 About 436.91.

The first choice is near \(2^6\), but rounding its factor to 64 while retaining \(n=127\) and \(\alpha=2\) breaks the exact scale identities. A power-of-two implementation must reconcile the chosen range, representable weights and bias/output factors rather than mixing exact and approximate parameters.

Weight bounds require actual range measurement and, if chosen, training regularization or clamping; floating-point training alone does not guarantee them. A useful sufficient accumulator bound is:

$$ |\overline b|+\sum_j|\overline W_j|\,|z_j| \leq \operatorname{max}_{\mathrm{accumulator}}. $$

Storage width and computation width are separate decisions. In particular, an activation fitting int16 does not prove that its pre-clipping sum fits int16, and int32 must be checked against fan-in as well as individual parameter ranges. These cautions apply to integer-design experiments; the actual mixed implementation remains defined by quantization.hpp, weightReader.hpp and layer.hpp.

SIMD and scalar layout

Serialized dense matrices are arranged as input-major values. When USE_SIMD_INTRIN is enabled, WeightsReader::streamW() transposes to output-major rows:

destination = (serializedIndex % outputWidth) * inputWidth
              + serializedIndex / outputWidth

SIMD inference computes one dot product per output. The scalar path keeps input-major layout and accumulates scaled output rows. Export order must match the loader, not whichever in-memory path was inspected.

There is also an actual input-activation distinction: the non-SIMD path dequantizes first, then calls activationInput, whose upper bound is Quantization<true>::scale, currently 512 rather than 1. The normal fused SIMD conversion clips to 1. Thus same topology is not a proof of identical outputs. This is a documented path difference, not a change made by this guide.

Incremental update cases

For a non-king quiet, each perspective erases the old source row and inserts the destination row. A capture additionally erases the victim from the proper us/them category. Promotions insert the promoted kind instead of another pawn. EP removes the victim at oldEP +/- 8, not at the moved pawn's destination.

Move Accumulator work before propagation
Non-king quiet Two row operations per perspective.
Ordinary non-king capture Three row operations per perspective.
Promotion / EP Same row-delta principle, with special kind/square selection.
King changing block Rebuild mover's perspective; update the unchanged opponent perspective.
Castling with king-block change Rebuild both perspectives, accounting for rook relocation.
Null move Board features unchanged; side-to-move input order changes.

The updater receives MoveInfo made before board mutation. When it runs, p.c has already flipped, so mover is ~p.c. Losing that distinction swaps feature ownership while leaving the board itself apparently legal.

With getBlock(k) == k, an ordinary moving king always changes block. The dispatcher nevertheless checks same-block equality; a stationary-king Chess960 castle can take that other branch. Do not assert that every castling encoding universally enters the two-perspective reset path.

Work estimate

Ignoring memory latency and vectorization, an ordinary quiet modifies 2 * 2 * 384 = 1536 accumulator elements; a capture modifies 2304. A full one-perspective reset inserts roughly occupiedPieces * 384 elements. The active dense bucket has 6360 matrix weights used in its scalar products.

These counts explain why copying/updating accumulators and cache misses in large randomly addressed input rows can dominate. They are not measured cycle counts, and they do not predict Elo or complete nodes per second.

Association, dirty state and deferred updates

associateEvaluator() stores a pointer and marks the evaluator dirty by default. Root setup associates its slot and performs a full reset. Child setup copies the parent's evaluator values into the child's slot, associates them and then applies row changes. Reset/update finishes with dirty = false; propagation asserts it is not dirty.

Dirty state is a validity marker, not a general automatic memoizer that silently repairs every invalid position on propagation.

Main search applies board moves with NNUE update deferred until after legality and pruning. A pruned board child must never be propagated before proper association/update. With DEBUG_NNUE_UPDATE, a fresh evaluator rebuild is compared to the incremental state after update.

Optional prefetch exists for upcoming feature rows but is disabled. It changes memory scheduling, not mathematical evaluation.

Training-only factorization

The trainer uses withFactorizer = True. Its piece_position(i) drops the king dimension by mapping the feature index modulo 768.

Each full king-conditioned transformer receives a shared piece-position factor contribution during training:

virtualExportWeight = affineWeight + expandedFactorWeights

This shares a simpler positional prior across king squares while retaining king-specific residual freedom. Serialization folds it into the ordinary 49152-by-384 matrix. There is no additional factorizer layer during inference. The exported bias remains the affine bias.

The C++ sparse loader sorts active feature indices into coalesced batches and provides side-to-move, outcome, score and bucket. The Python dense fallback uses halfka.py; matching its tensor orientation to the primary sparse feature path is an explicit requirement, not something the architecture name proves.

Loss and uncertainty units

With network scalar z, labelled engine score s and outcome t:

q      = sigmoid(600*z / 360)
p      = sigmoid(s / 410)
target = lambda*p + (1-lambda)*t
error  = abs(target - q)^2.4

Current sample weighting uses outcome-surprise weight normalized to batch mean. Calculated score-zone weights are not multiplied into the active expression. Commented dropout calls do not make the active model a dropout network.

The optional head returns exp(clamp(logVariance, -10, 10)). With a positive uncertainty training weight, the loss mixes the powered-error term with:

v = clamp(predictedVariance, 0.1, 10)
NLL-like term = 0.5*log(2*pi*v) + error/(2*v)
penalty = 0.01*mean(predictedVariance)

WITH_NNUE_UNCERTAINTY is disabled in the normal build. Without that head, C++ propagation returns uncertainty 1; this is a placeholder, not a measured confidence estimate. Python defines and exports the head even when its uncertainty loss weight is zero.

Because error is a power 2.4 in sigmoid-target space, this is not automatically a calibrated Gaussian variance in engine-score units. A variance for a score scaled by a would ordinarily scale by a^2; a nonlinear sigmoid conversion requires a different transformation or direct calibration.

Correction history estimates signed systematic bias; this head estimates a different uncertainty-related target. Neither absolute correction nor this variance alone proves tactical safety.

Export/loader contract

The stream contains version, white transformer, black transformer, then both bucket instances of fc0, both fc1, both fc2, both evaluation heads, followed by optional uncertainty heads. It is grouped by layer, not "all layers of bucket 0, then all layers of bucket 1".

The version is 0xc0ffee03; byte-size and version checks determine compatibility. A head-disabled engine accepts the optional tail and ignores it. Enabling the head expects that tail and does not supply learned weights for an older file.

The byte stream uses native numeric representations; it is not a checksummed, explicitly endian-neutral container. With WITHOUT_FILESYSTEM, the external file-size precheck is compiled out. Format compatibility does not guarantee that every float is finite or that accumulator sums will stay in range.

Always change feature indices, dimensions, export grouping, bucket logic, binary validation and both inference layouts together. Check known positions through trainer output, exported scalar/SIMD inference, and incremental versus reset inference before treating a topology modification as a search experiment.
